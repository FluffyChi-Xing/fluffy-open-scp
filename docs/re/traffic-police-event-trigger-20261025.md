# 警车随机警情的事件触发采样（2026-10-25）

## 动机

抢劫不是固定周期事件。固定抓取 60 或 180 个游戏 tick 只能说明窗口内观察到的状态，不能说明城市没有发生抢劫；事件可能在窗口结束后才出现。截图中的流程已经给出可用于对拍的三个锚点：建筑出现“行抢进行中”、警车追捕罪犯、警车显示“带回/返回警局”。

## 工具改动

`traffic_tick_watch.py` 新增：

- `--trigger-sink N`：等待任意逐车交易的**当前 sink**等于 `N`；候选列表中含 `N` 不会触发。
- `--post-trigger-ticks N`：触发后继续记录指定 tick，默认 30。
- `status.json` 和 `summary.json` 写入首个触发 tick、Agent key/地址、TransportEntry 和候选列表。

等待模式在未触发时运行到 `--seconds`，因此不会因普通的 `--ticks` 短窗口提前结束。对本进程，`323` 已由脚本表精确闭合为 `CrimeInProgress`，可以作为第一次事件触发值。

## 现有窗口的验证

续采样目录 `tmp/traffic-police-followup-20261025` 共包含 155 个观察 tick、2,876 条警车 Agent 记录。当前 sink 计数为：

| 当前 sink | 观察数 | 解释 |
|---:|---:|---|
| 1122 | 1,730 | `PatrolPoint`，巡逻点目标证据 |
| 708 | 709 | 语义尚未闭合 |
| 109 | 437 | 高度疑似警务返回目标，名称尚未直接闭合 |
| 323 | 0 | 本窗口没有实际选中犯罪目标 |

但是三种候选列表合计覆盖全部 2,876 条观察，并且都包含 323：`[708,323]`、`[323,1122,109,5]`、`[323,109,5]`。这证明候选列表是任务/路线的备选集合，不能当作已经发生抢劫或已经出警。

窗口内同一 transaction key 的当前 sink 转移为 `1122→708` 169 次、`708→1122` 177 次、`708→109` 39 次、`1122→109` 2 次；没有 `323→...` 或 `...→323`。因此不能把这些转移标成“抓捕押送”，尤其不能仅凭 `708→109` 宣称已捕获罪犯。

## 事件触发式窗口的实际命中

随后启动 `--trigger-sink 323 --post-trigger-ticks 30` 的等待模式，在
`tmp/traffic-police-event-watch-20261025` 命中：

- 触发 tick：`72851`
- TransportEntry：`50 (PatrolCar)`
- transaction key：`15506`
- Agent 地址：`0x7d93eb04`
- 候选列表：`[323,1122,109,5]`
- `current sink = 323` 出现在 7 条观察记录（72851、72853–72856、72858–72859）

这次是实际选择犯罪目标的直接运行时证据，证明事件触发式监听可以解决随机事件的漏采样问题。触发期间该 Agent 的位置从约
`(-233,245)` 移动到 `(266,896)`，4 个路径段也连续变化；它不是只在候选列表里出现一个静态 ID。

触发后的同一 key 很快被新 Agent 地址复用，并转为另一个 sink（72861 起为地址
`0xa5e42f24`、候选 `[65,262,5]`），所以这一次仍没有看到同一车辆“到达犯罪点→押送回警局”的完整闭环。这个地址变化说明 transaction key 不能单独作为车辆身份；后续必须同时跟踪 Agent 地址、位置连续性和 TransportEntry。

## 三倍速监听的第二次命中

在游戏速度调到三倍后，使用 20ms 外部轮询和 `--post-trigger-ticks 300` 再次监听，结果目录为 `tmp/traffic-police-event-watch-3x-20261025`：

- 触发 tick：`74128`
- 同一 tick 同时有 6 辆 `PatrolCar` 选中 `323`
- 总观察：412 个 tick 行、6,567 条 Agent 记录
- 触发 Agent 中，`0x4fac2664`（key `2400`）在 `74128` 选中 `323`
- 同一 Agent 下一次观察 `74129` 转为 `109`，并在后续 tick 保持 `109`

在触发 tick 的六辆车中，交易位置至少分成两个明显空间簇：一辆约为
`(366,286)`，另外五辆约在 `x=849–900、y=-541~-891`。这与“多个激发态罪犯同时产生多个警情”相容，但 `transaction.position` 的目标点语义还未完全闭合，因此目前只能作为并发事件的支持证据，不能据此断言恰好有三个案件。

该 Agent 的可复核序列为：

```text
708 → 1122 → 323 → 109
```

其中 `323 → 109` 发生在同一 Agent 地址、同一 transaction key 上，不是 key 复用造成的假转移。这是目前最强的“出警后进入警务返回目标”证据；由于 `109` 的名称尚未从脚本表直接闭合，仍应标注为“高度疑似返回警局/警务目标”，不能直接写成“监狱”。

其余 5 辆车在触发后分别回到 `1122` 或离开观察集合，说明一次警情可能同时驱动多辆警车，或者存在多个并行警务交易。后续应继续寻找 `323 → 109 → 5`、`323 → 708` 等完整后继，并把 `CriminalsArrested` 资源变化作为抓捕确认条件。

## 建议的实际采样

在游戏中看到“行抢进行中”后，不要重新开始一个短窗口，而应提前启动等待命令；命令会保留事件前的普通轨迹，并在首辆警车实际选择 323 后继续记录 30 tick。随后还要以 Agent 地址和位置连续性为主键，把路径段、位置、速度和 sink 序列与截图中的建筑事件时间对齐，才有资格区分“出警抵达”和“抓捕后返回”。

这仍是进程外 `ReadProcessMemory` 只读观察：不注入、不暂停线程、不调用游戏函数、不写游戏内存。快照非原子，地址只对当前 PID 生命周期有效。

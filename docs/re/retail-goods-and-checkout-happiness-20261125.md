# 商业分档商品量与默认成交快乐

2026-11-25，按用户要求：快乐量不开放 UI，构建默认提高至 3；商品量按低、中、高价值分别配置。后续用户强调城市低收入人口远多于中、高收入，默认供给改为低／中／高约 4／2／1。

## 构建契约

- 新模块 `behavior_commercial_tuning.rs` 固定 `0E854247=3.0`。现有商业字段写入和成品回读共同检查此列，缺失或错误则失败。
- 原版 AEB `2D0AB109/2D0AB10A/2D0AB10B` 的特化项为 `propertyId=0E854247, opId=8, data16=1, data8=1`。引擎 `SpecialiseUnitRule`（`docs/source-code/SimCity-dev-ida.c:667743`）将 op 8 路由到 nearby 资源规则，`OverrideResourceOp`（663137）将 type 1 写入 output。因此改变的是顾客消费事务的 HappinessToken 输出，不改价格、付款输入或客流容量。原始购买规则和住宅返家规则不被替换。
- 新字段 `goodsW1/goodsW2/goodsW3` 各为 1–100,000 的整数。旧 `goods` 或配方默认值作为中档基准；未填写的低档取基准两倍，高档取基准一半并向下取整，最低 1、最高 100,000。显式分档值优先。旧字段继续可读取，UI 编辑后显式保存三档数值。三档全部显式配置后，不再依赖隐藏旧值。
- 沿用已验证的独立分档商业组件：最终每个 Unit 仅启用对应财富档接待器，并将该档商品量写入原生 `0DA3EE15`，不把三档商品重复写成同一个值。关闭某档接待仍由原有顾客容量 0 控制。
- 工作台保存/重开保留新字段；中英文标签同步更新。没有新增快乐开关或输入框。缓存输出版本升至 v22，避免无变化缓存回用旧快乐输出。

## 验证与边界

原生构建模块 328 项通过、0 失败、29 项原有忽略；包含三档 789/456/123 实际编译到独立组件、默认快乐 3、缺失快乐列拒绝通过、旧商品量继承和非法输入校验。前端相关 32 项通过，覆盖编辑/保存/重开及中英文切换；类型检查与生产构建通过。

这些证明构建数据和成交输出契约。住宅实际获得多少净快乐仍取决于原版返家分支、剩余钱、资源容量和其它快乐消耗；没有将静态 3 当作住宅一定净增 3 的游戏验收。人口面板“不满意”按商品供给缺口计算，快乐参数不会直接更改该数。

真实瓦科、泡芙和三档商品 fixture 均通过完整构建链与写盘回读。先验证实际部署包与 GOLDEN 的 SHA-256 相同，再逐资源解码对拍：瓦科、泡芙均仅三个商业 Unit 新增 `0E854247=3.0`；fixture 仅这三个 Unit 额外修改 `0DA3EE15`，分别为 123/456/789。资源身份集合相同，其余全部解码 payload 和属性记录不变，覆盖模型、材质、贴图、Graphics、生命周期、停车、统计柱和面板。

## 用户纠正后的低档优先配比

默认量以中档为基准，而不是按财富升高递增：瓦科基准 450 对应低 900 / 中 450 / 高 225；泡芙基准 750 对应低 1,500 / 中 750 / 高 375。UI 与构建器使用相同规则，重新打开旧混合商业配置也展示加权量；手动分档值不被改写。边界量会受既有 1–100,000 限制，比例仅在不触及边界和整数舍入时精确成立。

提高商品量会沿现有原版 `0DA3EE15` 商品库存与日商品登记路径生效；没有直接改人口统计结果或强制清除“不满意”。城市供给缺口是否下降和住宅是否恢复仍需运行期验收。

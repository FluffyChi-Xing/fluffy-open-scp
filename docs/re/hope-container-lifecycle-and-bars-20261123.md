# 希望大厦容器：夜间回归与柱图重叠

用户确认 v4 面板已能显示维护费、游客数；仍反馈夜间窗户不亮及多个柱子重叠。不能将前次包围盒修改称为排列问题已解决。

## 灯光基础接线回归

当前已部署参照先验 SHA-256 为 `9eb140f03e72349dae11cc9f9f45a681bbbaf2b3b681835b203720f053a536e2`。保留了相同字节的工作区副本。

Graphics Unit/Lot 的 `0F169C46` 开关存在，宿主也引用 `406CCC43`；因此不能把本次问题简单描述成缺少该灯光开关或地标激活 bundle。

原版 `SC/cGraphicsUnitInteriors/Update.c` 硬编码读取本 Unit 的 bit29 ActiveBuilding，设置亮灯比例；不会自动读取连接组件的活动标志。`CreateGraphicsUnitInteriors.c` 与 `FillFromProps.c` 也只处理所传入 Unit 的本地状态。

普通宿主移植了巨塔基座的 B2 排除表，其中包含基础经济/生命周期包 `30645625`，却未移植巨塔的替代实现。这使已有 `406CCC43` 激活链的资源前提缺失。原版脚本库回读 `30645625` 可见 ActiveBuilding bin、WorkersNeeded 映射及启停规则等基础接线。它与具体的办公、住宅、观光配方不同；宿主岗位属性仍全部为 0，业务组件保持隔离。

当前定向候选仅移除宿主 B2 中的 `30645625`，恢复其已存在的原版启用引用；没有增加假劳工或自定义常亮规则。新增闸门要求生命周期 provider 和地标激活 provider 均有效，旧版仅检查 Graphics 开关/控制器与 bundle 引用不充分。

注意：这是已确认的基础接线缺失和针对性候选修复。静态检查无法证明它是夜间回归的唯一原因，或现有存档加载后一定恢复灯光；仍需用户游戏内确认夜间、整栋启停和重新放置的结果。

候选 SHA-256 `f2b3a4b2b29df4cec4224160a2a5a4dfe7adbe01110c14073aed36efe280902c`，共 29 资源。与实际部署参照先验哈希后比较，仅宿主 Unit 的 B2 少一项 `30645625`；业务组件、模型、纹理、面板及其余资源解码 payload 逐字节不变。见 [证据](evidence/hope-container-night-20261123.json)。希望大厦及六类组合均通过完整构建和 DBPF 回读。

## 柱图排列仍未完成

**后续零售版调查已推翻本节的能力边界推断。** 当前零售版存在基座汇总表及 `0FB2DB9A` 分组字段；新增接线和当前 EXE 字节核对见 [原版柱图汇总](hope-container-native-bar-grouping-20261123.md)。下文保留为仅适用于此前开发版源码的调查过程。

原版 `SC/cBarGraphManager/UnitCreate.c` 和 `Update.c:380–408` 以 Unit slot 为键保存柱图。只有同一个 Unit 的多个柱子才按照 `mBarFootprint` 横向排列：起点为 `footprint/2 - count*footprint/2`，步进一个 footprint。不同 Unit 的排列各自从本 Unit 原点开始。

所有业务组件都挂在相同位置，导致各自的柱图组重叠。v4 复制建筑包围盒只能使长轴判断一致，不能改变按 Unit 分组的事实。进一步偏移包围盒中心也不会起作用，原版这里只使用包围盒的轴向尺寸。

本轮没有通过移动业务组件原点或改动道路入口来伪装修复。这样的操作会影响 sink 位置、邻近搜索等模拟语义，需要额外证明，不能仅凭显示结果宣称无影响。需要继续实现独立的统计汇总/显示分组契约，或找到原版可用的显示分组能力。当前候选不声称已修好柱图排列。

# 菜单编辑与资产编辑的新启示：威利斯结构模型与消防局价格案例复盘（2026-10-27）

本文回答两个问题：威利斯大厦纵向研究（`willis-tower-landmark-mechanism-20261027.md`）对菜单编辑器和资产编辑器分别意味着什么；以及用这套新结构模型重新审视"消防局复制到道路菜单、单价 20000→20 后游戏内词条乱码 + 无法铲除"的历史异常（原始调查见 `fire-station-economy-anomaly-20261020.md`）。结论边界保持不变：该异常包已丢弃、无运行时取证，本轮不能也不会宣称已定根因；能做的是把风险从"泛泛的可能性"收敛成"具体的、可判别的机制清单"。

## 1. 威利斯研究给出的结构模型

```text
菜单层（归属）                    模拟层（行为）
Menu2 0x00B1B104                 EcoGame Unit 40E0C000（叶子）
├ uiCategories  → 挂哪个菜单     ├ 0x00B2CCCB → 服务模板 48E0C000（4E01E311/BD7BF4A1/…）
├ parent       → plop根/道路根   │   ├ 类别绑定 0x099B4C1F / 0x0AFE27B1
├ menuUnit     →→→→→→→→→→→→→→→ ╋ → │ ├ 费用科目 0x0AD65F07/08
├ unlock 三件套 0x0DE84Dxx       │   ├ 解锁/限额 0x0BF5D2E3·E4 / 0x0E51C90F / 0x0CC8BE51
└ 统计行 0x0EB1FC05·FC22 ──────╋─→ └ 叶子覆盖：造价/维护/水电/垃圾/吸引力/15个bundle
   （参数=Unit属性哈希直引用）     │
                                 Lot 层 40E1C000（放置/模型/锚点/路径，无经济字段）
                                 └ 0x00B2CCCB → Lot 模板 40E1C000（与 Unit 模板同 instance！）
```

三个本轮新确认、编辑器必须知道的事实：

1. **每个服务类别有两套同 instance 模板**：`BD7BF4A1` 既是火灾 Unit 模板（`48E0C000`，含功耗默认/类别绑定），又是建筑 Lot 模板（`40E1C000`，含 bbox/模型引用）；地标 `4E01E311` 同样双注册。**只按 instance 寻址无法区分它们**。
2. **同 instance 跨 group/跨包冲突是常态**：威利斯 `74168A83` 在 Graphics 包是 Menu2（292B）、在 Game 包是 rollover JPG（91841B）；消防局 `E917279C` 在 Scripts 包是 Unit（707B）、在 Game 包是 Lot（3335B）。instance 相同、schema 完全不同。
3. **UI 数值与 Unit 属性是"哈希直引用"**：菜单统计行 `unitEffectParameter` 里放的正是 Unit 上的属性哈希（威利斯 `[0x0E542F39, 0x0E585AE0]`）；rollover 的维护费查询读的是 bin `4227066323 = 0xFBF3E9D3 = kResourceIDExpensesFromMaintenance`（本轮命名）。

## 2. 对菜单编辑的新启示

1. **"移动/复制菜单"只应触碰归属边**（uiCategories、子栏容器、面板布局），经济与行为编辑必须落到 menuUnit 指向的 Unit。复制菜单不复制行为主体——副本与原版共享同一个 Unit，价格互脐。编辑器 UI 应显式提示"此条目与 N 个其他菜单共享模拟主体 E917279C"。
2. **显示价是"menuUnit + 子单元一层求和"**（`cToolPlop::FillFromProps` 已核）。编辑器改价后应按同一条求和规则回显预览值，而不是显示写入的裸值；否则用户以为改了 20，游戏显示 20+子单元造价。
3. **统计行的"乱码"有明确机理**：`~population_amount:number~` 这类占位符原样显示 = 该行的数据绑定失败（UI bridge 单条必需查询返回 null 即拒绝整批回调，已由 `tools/audit-fire-rollover.cjs` 在零售脚本上验证），**不是** locale 编码损坏。两类"乱码"要分开诊断：占位符未绑定（模拟数据链断）vs 文本真乱码（Text 引用/520 步长写坏）。
4. **解锁与数量限额分散在两处**：菜单解锁三件套（`0x0DE84DC9/DD3/DDC`，Key+数量+文案必须成对）和模板/容量层（`0x0BF5D2E3·E4`、`0x0E51C90F`、共享容量数组 `0x0A8DF590/91/92` 按下标配对）。只改文案不改 Key、或只改一处容量，都会出现"显示能建/实际不放"或反之。
5. **条目寻址必须 TGI + 领域约束**：Menu2 按 group 低 16 位区分工具（`8A01`）与容器（`8BDD/BA03/C900…`）；覆盖包必须与源同 group 才命中同一条目。现有导出"按 instance 取路径数字版本最大者"的候选逻辑，在同 instance 多注册事实面前是结构性隐患（见 §4.2）。

## 3. 对资产编辑的新启示

1. **一切数值默认值都在模板，叶子只写覆盖**。威利斯吸引力模板 500→叶子 400、观光收入 15→11；火灾模板功耗默认 72/80/240 与叶子 72/15/45。编辑 Sheet 应标注每个字段的"生效来源"（模板默认 or 叶子覆盖），写回时"写叶子、保 parent"（数量上限研究已有此守则，现推广到全部字段）。
2. **改共享模板 = 广播改动**。火灾 Unit 模板 `48E0C000:BD7BF4A1` 被两栋火灾建筑共享；Lot 模板 `40E1C000:BD7BF4A1` 同理。对模板的任何写回必须列出受影响建筑清单并要求确认。
3. **水/电族字段整族一致**：`Amount × 3 = Capacity`，且各有一个与 Capacity 同值的伴生哈希、一个恒 0 的伴生哈希。数值 mod 应整族联动修改，只改一个字段会造成 UI 显示与实际 bin 脱节。
4. **bundle 是行为的挂载点**：叶子 `0x0A0209A5` 启用、`0x0A0209B2` 排除、模板 `0x0A0209A4` 候选。增删 bundle = 增删一类规则/资源 bin；bundle 内 `0x07E0AD23/24` 的资源与容量必须成组拷贝。
5. **Lot 编辑与行为解耦**：bbox/前缘/路径/UnitLocation 锚点（如威利斯塔尖 `top_tip`）影响放置与 agent 走位，但不产生模拟行为；effect 是独立实例键，"没有 effect 键"的地标属正常形态，不要以"缺 effect"为由改 Lot 结构。

## 4. 消防局 20000→20 案例复盘

### 4.1 本轮新增的静态事实

对原研究未覆盖的模板层与 bundle 层补 dump（原版资源，非异常现场）：

- 消防局叶子 Unit `40E0C000:E917279C`：造价 `0x0A8A41DA=20000`、维护 `0x09AE19D7=400`，**费用科目在叶子上**：`0x0AD65F07 → F3DA2D8F（ExpensesFromMaintenanceFire）`、`0x0AD65F08 → 83ACB4DE（ExpensesFromFire）`；类别绑定 `9FAC79C9`（kCategoryIDFire）；解锁 `C93FD4B5`（市政厅）；水电 15/45（又一次 1:3）；4 个 bundle + 排除项 `F90C8A94`；`0x0CC8BE51=4`。
- 火灾 Unit 模板 `48E0C000:BD7BF4A1`：**没有**造价/维护/费用科目字段，只有功耗默认（72/80/240）与类别绑定；parent → `2A25CF66`（Toy 层）。
- 消防局 Lot `40E1C000:E917279C`（3335B）：parent → `40E1C000:BD7BF4A1`——**与 Unit 模板同 instance 的 Lot 模板**。
- 消防局 4 个 bundle 的资源表均不含 `0xFBF3E9D3`（通用维护 bin）；该 bin 是引擎标准 bin，不由 bundle 资源表创建。

### 4.2 新研究改变诊断的三个事实

1. **rollover 的 `kMaintenance` 查询对象现在有名字了**：`bins/4227066323` = `kResourceIDExpensesFromMaintenance`（通用科目）。而消防局叶子把维护记入火灾专用科目（`F3DA2D8F`）。"通用 bin 由谁从专用 bin 汇总"此前不可问，现在是一个可定向验证的问题（见 4.4）。若特化或规则链断了，null 的就是这个查询——与整批绑定被拒（乱码）衔接。
2. **"无经济字段时改父模板"分支对消防局本不应触发，但双注册使误写共享资源成为具体风险**：叶子上有价格与维护字段，正常解析走叶子。但历史异常包出自旧版导出；当时若 `gamePropertyRead` 按 instance 把 `E917279C` 解析到 40E1C000 的 Lot 资源（同 instance、在"路径数字版本更大"的包里），就会得出"无经济字段"→ 把价格写到 Lot 资源或其共享 Lot 模板 `40E1C000:BD7BF4A1` 上。这解释了为什么"复现测试全绿、历史包仍异常"：现版本代码（store 回归 17 项通过，唯一 patch = `40E0C000:E917279C Float 0x0A8A41DA=20`）已经绕开了这个坑，而当时生成的包可能没有。
3. **"无法铲除"与"乱码"可能同源**：两者都依赖 placed building 的 unitref 解析链。详情页绑定（unitref → bins 查询）与铲除（unitref → tool/Unit 匹配）读同一条特化结果；特化失败或 Unit 身份漂移会同时表现为"详情占位符原样显示"+"铲除找不到目标"。这把两个症状从两个独立 bug 收敛为一个候选根因族。

### 4.3 判别性验证步骤（按优先级，可执行）

1. **用当前版本导出重做一次 C 包（价格 20）并保留原件**，进临时城市放置，`ui-observer/native_trace.py --profile bridge-commands` 现场抓 `Null data binding data` 或 JS 异常（原研究已给出该步骤，仍是第一优先）。
2. **审计历史包是否仍在备份/回收站**：检查其中是否包含 `40E1C000`（Lot/Lot 模板）或 `48E0C000`/`40E1C000:BD7BF4A1` 的写回——若含，4.2-2 的机制即被证实；若只有 `40E0C000:E917279C` 单字段，则该机制被排除。
3. **定向规则采集**：城内放消防局后 `rule-logs/capture.py --scope unit-consumption --resource-id 0xFBF3E9D3` 与 `--resource-id 0xF3DA2D8F` 各采 30 秒，回答"通用维护 bin 是否存在、由谁写入"；价格 20 与 20000 各做一轮对照。
4. **铲除路径取证**：异常建筑上读其 unitref 的 Unit 身份（`cEcoUnit::mID`，偏移 +0x0C，小学研究已验证），比对 `E917279C` 与模板链，判断身份漂移发生在特化层还是菜单层。

### 4.4 边界

异常包已丢弃、无运行时取证；本轮新增全部为原版静态证据。4.2 的机制是"与全部已知事实相容、且可被 4.3 判别"的候选，不是定案。

## 5. 编辑器守卫清单（可落地）

| # | 守卫 | 依据 |

| 1 | 所有资源读写按完整 TGI + 领域 group 约束寻址，废弃 instance-only 候选；候选冲突时枚举并列而非取"版本最大" | §1 事实 1/2 |

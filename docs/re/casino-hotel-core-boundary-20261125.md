# 罗马幸运赌场：博彩与酒店行为边界（2026-11-25）

状态：原版资源与规则静态研究完成；下文是构建器实现边界，不代表新增节点已经实现或获得游戏验收。本次没有改动游戏包、存档或已验证的住宅、观光、公园、商业、办公配方。此前已验收工作已提交为 `b9d5349`。

## 1. 结论与样本身份

赌场有两条相互衔接、各自守恒的链：

| 链 | 核心过程 | 不能混入的内容 |
| --- | --- | --- |
| 博彩 | 发布吸引力和接待位 → 接收游客 → 占用博彩容量 → 按财富档游客计收入 → 归还接待位/转住宿/离开 | 客房人数不能重复算作正在博彩人数；犯罪、DLC解锁、赌场外观不属于博彩核心 |
| 酒店 | 发布空房 → 接收游客或内部转为房客 → 占用房间 → 退房归还空房 → 返回博彩或离开 | 不能预填房客人数；不能把 `ProfitToken` 当作现金；不能引入自长建筑施工/废弃机制 |

水、电、污水、垃圾、宿主激活、整栋开关仍由已验证的 plop 容器承担。清理这些设施职责不等于删除业务状态：空房、接待位、入场条件、关闭清退、全城登记和移除时撤回是行为闭环的一部分。

| `SimCityDLCRomanCasino-Scripts_276985846.package` | `9833b5908a17ce740ac90014e048305e241a7ca6b03315b91edf0c9536290a7f` |

赌场本体为 `00B1B104:55EFC000:A94FB11E`，继承 `48E0C000:9F25895C`；普通赌场对照为 `40E0C000:3CE0F852`，普通中收入酒店对照为 `40E0C000:6F05DD57`。罗马脚本 AEB 为 `08068AEB:40800201:C9003F87`；通用脚本 AEB 为 `08068AEB:40800200:622B9CD7`。

## 2. 博彩接客与盈利

业务提供器候选：`E15369A2`（吸引力/财富档配额），`75D22FD1/75D22FD0`（中/高收入游客接待及离场），`3B8EEF5B`（博彩收入、结算和撤回）。这不是已经证明足够的四项清单：营业模式、库存补充、全城发布与关闭清退依赖必须一起满足。

本体参数与截图不同：本体吸引力 `0E542F39=250`，财富配额 `0D8C29F6/FE/2A01=0/300/300`，`OpenShoppers` 容量属性 `0AD6A725=400`，博彩容量属性 `0EF29855/56/57=0/200/200`。截图含玩家已建模块，不能把截图 640 游客、200 客房反推为本体默认值。

W2 接客 `64E8EB51` 消耗事务中的 `TouristW2`、本地 `SouvenirsW2` 和 `OpenShoppers`，增加本地游客与 `TotalShoppers`；后继 `2B3A2553` 涉及 `GamblerCapacityW2`。这些字段各有职责，不能只留下显示柱的游客 bin。停留时间属性 `0D9114D4` 原型为 **Vector2**，本体 `[120,120]`，不能降成标量。

`3B8EEF5B` 的四个收入刷新根在 hour 周期的 `0/.25/.5/.75` 触发（priority 5），经 `3ADA8373` 撤回上一轮本地/全城收入，再执行：

| 规则 | 消费基数（读后保留） | 费率属性 |
| --- | --- | --- |
| `56EB692B` | `TouristW1` | `0EE2A50D` |
| `7539D246` | `TouristW2` | `0EE2A50E` |
| `03FE64B1` | `TouristW3` | `0EE2A50F` |

属性特化将输出乘费率，写本地及全城 `IncomeFromCasinos(4E1450B0)` 与 `Income(107FCDCC)`。罗马本体费率为 `10/20/40`。用户截图可独立核算：

`114 × 20 + 406 × 40 = 2,280 + 16,240 = 18,520/小时`。

193 名饭店客人没有加到这个公式里。该公式解释的是截图当下的收入，不能据此复算整天利润；整天利润还取决于时序客流与维护支出。

`16BA06E0`（hour、priority 7）从收入与 `ExpensesFromMaintenance(FBF3E9D3)` 累加当期账本；`6677D489 → 50290557 → C350EF5C → 96E1277E` 负责周期滚动与显示。保留原始周期 `12952639` 和触发相位，不根据 catalog 的 Month 命名自行换算时间。`E20CDC92` 负责移除撤回。

通用面板账本 `C14044C4` 和赌场账本有重叠 bin；同一 Unit 不能简单叠加两套结算。组合配方还需核对收入汇总到宿主、宿主维护费只记一次、全城收入只发布一次。

## 3. 饭店客人：空房发布是必需环节

赌场住宿核心 `352F4263` 声明三档 `GuestW*`、`OpenGuestsW*`、`TotalGuests`、待退房与超额处理状态，**房客与空房初始均为零**；它没有把客房属性绑定到初始化值的 `0A6FE749…74E` 表。把 `0E2660C6` 写到本体上不会自动产生可入住的空房。

原版是客房模块向相连本体发布空房：

| 模块样本 | 提供器 | 客房属性 | 发布规则 |
| --- | --- | --- | --- |
| `E44B84A9`、`93B11535` | `1A5BDAC5`（W2） | `0E2660C6=60` | `C4B844DB → A2DAAF96` |
| `C24049C6` | `9E4D2B6E`（W3） | `0E2660C6=40` | `C4B844DA → A2DAAF97` |

模块本地缓冲 `8E9C60E3` 容量绑定客房属性，先按剩余容量填充，再通过连接目标写入 `OpenGuestsW2/W3`。这解释了房客提供器为什么不能单独复制使用。模块还含客房全城统计、待退房转交、超额处理与容量撤回；`E365A124` 的模块数量登记不能代替空房发布。

普通酒店 `729A6626` 则直接将空房初始化绑定 `0E2660C6`。两种都是原版设计，但不能一半用赌场动态模块回收、一半用普通酒店初始化而不处理所有权，否则会出现零空房或重复空房。后续普通单体酒店可以选择更简单的原版初始化路线；赌场组合酒店必须明确房间发布的目标 Unit 与连接作用域。

## 4. 游客 → 房客 → 返回博彩/离开

原版存在两种入住入口：

1. 城市游客寻房：例如派发规则 `13FC9444` 的候选目标包含 `729A6626`；游客离开其他目的地的 `0CACE342` 也可转发至该入口。到达 W2 入住规则 `774570F5` 后：`GuestW2+1, TotalGuests+1, OpenGuestsW2−1`，消耗事务游客，并发出 `8645F30B` 后续事务与生命周期计时。
2. 同一赌场内部转房：W2 游客后续链经 `0D0C535E` 到 `4EEE2726`，**游客−1、TotalShoppers−1、OpenShoppers+1、房客+1、TotalGuests+1、OpenGuests−1**。它不是凭空再生成一个房客；博彩位置得到归还。

W2 房客后续入口 `8645F30B → 75167B09` 检查待处理状态、场所标记与事务条件；满足博彩库存时执行 `6B2532D1`：

`GuestW2−1, TotalGuests−1, OpenGuestsW2+1, TouristW2+1, TotalShoppers+1, OpenShoppers−1, GamblerCapacityW2−1`。

不满足时走 `95BAEBB6` 的其他目的地/离开分支；`6EA6E257` 会归还房间，把房客还原为事务游客，再发往 `75D22FD1/4DEC347C`。删除这些分支会让房客只进不出。计时记录中的 `60/10` 保留原生数值，本研究未将其强行解释为现实分钟。

这两条链在原版赌场**同一业务本体中共享库存**。以后若把博彩叶和酒店叶编译为两个私有 Unit，就必须显式桥接接待位、房间及转移事务；单纯把各自 bundle 放到两个 Unit 上不具备相同语义。也不能因“纯粹行为”而删掉这一业务连接。

## 5. 酒店收益不能与赌场现金混淆

入住后 `82DBB772` 写入的是 `ProfitToken(CF526BAE)+2` 与 `HappinessFromTouristCustomers(73B4629D)+2`；部分条件走 `5AECE3FA` 追加 token。它没有直接写 `Income`。

因此赌场研究证明了住宿循环和博彩现金循环，却**没有证明普通酒店房租已经具备独立现金结算闭环**。现有 `behavior_hotel.rs` 仍带普通 RCI 盈利/幸福度等提供器，其中 `6827D126` 不能未经拆解直接搬入不会废弃的 plop。酒店节点下一步必须单独界定原版 token 如何进入盈利状态，以及自定义可收取的房费如何入账；不能按每个 token=2 元等未经证实规则伪造收入。

## 6. 接客开关与解码纠正

`docs/source-code/SimCity-dev-ida.c` 的 `cSinkEntry::FillFromProps`（约 700820–700975 行）区分 flag 的测试集合与期望布尔值。解析器 `inspect_park_route.parse` 对 BOOL 返回 `rawBytes` 占位信息；它不是 true。旧笔记中“所有列出的 flag 都必须 true”的读法需要以原始字节纠正。

| Sink | flag 索引 | 对应期望值 |
| --- | --- | --- |
| 酒店 `729A6626` | `8,19,21,29,14,20` | `false,true,false,true,true,false` |
| 中收入游客 `75D22FD1` | `8,19,21,29,14,46,49,28,20` | `false,true,false,true,true,false,false,false,false` |

酒店 key resource 为 `OpenGuestsW2`，游客还有 `OpenShoppers/GamblerCapacityW2` 辅助测试。`0B555629` 是原生 `mResourceInvert`，`0DA7921B` 是 `mResourceConnected`，两者在酒店 sink 均为 true。不能仅根据 key 名把测试解释为“本地空房 > 0”；必须按引擎的 invert/connected 语义连通容量提供方。

游客原版补货规则还读取 `4B16C93D` 营业模式（例如 `CCD1142B/414F8467`），按时段补充纪念品和全城配额。已验证的巨塔观光发布路线不能直接替换此部分，因为它不自动提供博彩容量和同场住宿库存。构建器须显式选择并验证营业/补货契约，不能留到游戏里碰运气。

第二处解码修正：AEB 每条规则 transport 记录从 `fileOffset+136` 开始，每项大端 `Iff`；记录总长仍为 `144+12×count`。旧解析器以 `+144` 读取会错位，产生 `BF800000` 等伪 sink。证据摘要使用修正后的布局。

## 7. 后续构建器契约与验收

新增模块，保留所有当前 GOLDEN 配方。候选边界如下：

| 职责 | 保留 | 排除/不能整包复制 |
| --- | --- | --- |
| 容器 | 当前已验证水电垃圾污水、开关与渲染生命周期 | 不新增第二水电消费者 |
| 博彩叶 | 原版接待/归还/停留、博彩容量、营业补货、按财富计收入与撤回 | 犯罪 `1283EFC5`、解锁、DLC身份、外观模块、RCI废弃 |
| 酒店叶 | 空房发布/撤回、三档入住退房、转移失败出口、必要全城登记 | 自长施工、地价密度升级、RCI废弃、预填假房客 |
| 组合 | 明确库存所有者，保持同场游客↔房客转移，汇总账本/统计柱 | 重复收入、重复房间、两个独立设施入口 |

`1283EFC5` 是犯罪相关提供器（包含 CriminalRobber/Robbery），不是博彩盈利提供器；不能因赌场原型带它就纳入最小博彩配方。

实现时构建期硬闸门至少检查：所有 sink/rule/provider 引用可解析；三档容量与接客测试作用域一致；接客/离开成对归还；发布/移除成对撤回；共享 bin 无重复所有者；收入/维护费无重复结算；宿主关闭能停止接客并清退；所有子行为无新增水电垃圾入口。继续继承现有内景、六槽材质、夜间生命周期及统计柱闸门。

游戏验收另行记录：单博彩、单住宿、博彩+住宿三组需验证实际流入/退房/客流变化、满房、容量减少、整栋开关和账本；房客在睡眠时不能同时计为本场博彩游客。核对日夜灯光与材质、统计柱及共享面板。必须独立菜单项，用户冷启动，不覆盖原版资源，不更动持有健康样本的城市包集合。

本次仅做离线提取（完整临时 JSON 约 7.24 MB），没有增加全城快照或运行时采集。静态核对包括接客 flag 真值、transport 首项、赌场住宿无初始化绑定、截图费率计算，以及三个现金计费规则不读取 GuestW*。

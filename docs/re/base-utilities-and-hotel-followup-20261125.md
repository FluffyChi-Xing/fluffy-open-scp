## 水电圆圈不是直接的消费速率

原版 `cPipeOverlay::DrawSinks`（`docs/source-code/SimCity-dev-ida.c:995293`）读取所关联资源 bin 的容量（12 字节 bin 记录的 +8，另见 `probes/runtime/unit_resource_watch_generic.py` 的 `<hHii>` 布局），在约 995491–995530 行计算：

`radius = sqrt(capacity × capacityScale / π)`。

随后施加分支宽度下限、建筑边界尺寸上限和短暂动画。颜色还读取入口容量/最大容量的比例。因此圆圈可以反映缓冲/接待容量变化，不能直接当作单位时间消费；圈小本身也不证明该楼没有消费。修改单次量会经原版三倍库存关系间接影响圆圈，间隔则改变消费检查调度。

## 博彩和酒店的新增边界

此前 [赌场研究](casino-hotel-core-boundary-20261125.md) 的博彩收入公式、游客转房客、退房/返回博彩已经从原版规则追出，可以据此着手新增独立节点/处理器；当前生产代码还没有新的博彩节点，不能把研究结论当成实现完成。

本轮补齐了一个此前未定的引擎语义。`GB::SinkCapacity`（`SimCity-dev-ida.c` 约 653705–653780 行）：

- `mResourceConnected=true` 会将本地及相连单元的 amount/capacity 相加。
- 对 key resource，`mResourceInvert=true` 返回 **amount**；false 返回 **capacity−amount**。

酒店 `729A6626` 的 key 是 `OpenGuestsW2`，两项均 true，所以入口返回的是本地及连接单元的可用空房数。不能把这里的 invert 误解为拒绝有空房，也不能只把空房容量配好而没有 amount。

与此同时，原版入住 `774570F5` 的房客/空房增减写在 **接收单元本地**。如果多个独立叶子对外宣告一个连接求和后的空房入口，却将空房 amount 只放在另一单元，就可能出现入口有容量、实际入住扣不到本地空房的分裂。这是构建契约需要阻断的结构，不是对当前截图酒店故障的运行时定责。原赌场把空房模块发布到接客本体，避免了这个分裂。

普通酒店与赌场酒店仍有两种原版容量方案：`729A6626` 可用客房属性直接初始化自己的 OpenGuests；赌场 `352F4263` 则需要模块 `1A5BDAC5/9E4D2B6E` 的发布与撤回。新纯酒店配方应明确选择容量所有者，不混用两种方案。

继续沿 `6827D126` 检查，普通酒店现有路径的 `9D061D19 → … → D0981716/3021C1A4/4684DC06` 处理 `ProfitTokensToRemove/ProfitToken`；`C3EC8B4D` 的幸福度/经营路径也读写这些状态。该规则层不是赌场 `3B8EEF5B` 那套直接发布 Income 的现金结算。不能为了做酒店收入直接照搬普通 RCI 完整经营周期，带回密度/废弃/其他状态，也不能假定一个 ProfitToken 就是一元。

另将罗马赌场额外提供器按实际规则归类：`1283EFC5/9EADEAD2` 涉及犯罪，`78CB77BD` 涉及 NIMBY，`53BA360B` 涉及公园快乐，均不能因赌场原型带有就混入博彩核心。`CA726CB4` 的事件闭包又涉及营业模式 `4B16C93D`、游客及接待清理等多种库存，不能在未核对替代生命周期前简单删掉，或整包拷贝后声称是最小配方。

后续实现顺序：先明确博彩营业/补货与关闭清退的完整依赖，再接独立现金结算；酒店先固定本地空房和入住退房守恒，然后定义是否有独立房费（与赌场留客后再次消费的收入分开）。新增节点继续沿用当前公共服务、渲染与面板契约，现有 GOLDEN 住宅/观光等路径保持冻结。本轮不把尚未实现或未实测的博彩、酒店标成已可用。

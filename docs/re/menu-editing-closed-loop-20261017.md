# 从 SCP 菜单案例建立 OpenSCP 编辑闭环

日期：2026-10-17。范围：案例复核、当前代码核对、实现设计与验收方案；本轮未实现菜单编译器或部署菜单 mod。

## 1. 产品目标与证据

目标是让开发者选择一个游戏菜单项，就能看到其图片、文字、功能对象与资源来源，直接编辑、生成 mod 并核对游戏效果。资源浏览器和单文件预览是底座，不能代替这个开发流程。

本轮逐页查看 `C:/Users/FluffyCHi_Xing/Desktop/scp.pdf` 的 PDF 第 2–7 页（印刷页 75–80）。这些页面是扫描图，普通 PDF 文本提取为空；结论来自渲染页面的阅读。原教程为 Oppie: Basic modding，注明基于较旧 SimCityPak 版本。字段值须在当前安装重新确认。

### 教程实际做了什么

| 页面 | SCP 操作 | OpenSCP 应简化成 |
|---|---|---|
| 75–76 | 打开 Game 包，筛选 Property，找到 Pedestrian Path | 按显示名搜索菜单项，绑定真实源包与完整 TGI |
| 77 | 查看 Parent Menu；导出这一条 Property 到独立 package | 自动建立项目中的资源修改草稿，保留原始 Property |
| 78 | 找 Medium Density Avenue，从其 Parent Menu 复制道路菜单 Instance，粘贴到路径菜单项 | 在真实菜单树中选择“道路”，自动修改对应归属 Key |
| 79 | 保存 Property 后还要保存 package；同 TGI 覆盖使大学原入口消失 | 明确选择“移动入口”；一次构建保存，预览原位置移除、新位置出现 |
| 80 | 只更改复制出的 Property 的 Instance，保留 Type/Group，再保存 | 明确选择“复制入口”；自动分配无冲突身份，大学和道路各保留一个入口 |

**关键字段纠正：教程中的 Parent Menu 是 `0x0DB9FC63`，截图显示数组元素 `[0]`。它对应当前提取模型的 `uiCategories`，不是继承 Parent `0x00B2CCCB`。** PDF 第 78 页道路样本有多个 Parent Menu 元素，因此 UI 不能把它简化为只写一个永远固定的父指针。移动操作应替换选定归属，保留其他归属；重复目标应去重。

PDF 截图中路径菜单继承 Parent 为 `12E3214B`，原归属为 `9D2EF585`，道路目标为 `AC12C904`。当前静态 `public/game-ui/tools/tools.json` 中 `9A38E382` 具有相符的 Parent、归属与位置 10，可作为查找候选，尚不能替代对当前安装包的身份确认。

第 80 页没有要求复制模型、Unit 或纹理。它复用原始功能和资源，只增加一个入口。`ViewPropertyFile.xaml.cs:mnuCopy_Click` 是另一种更深的 Menu2 复制流程，不能把它的 Unit/LOD 复制步骤变成基础入口复制的前提。

这六页完整证明的是菜单入口迁移与复制教程；图片/文字字段在截图中可见，独立建筑克隆还可参考原 C# 实现，但不能将这六页描述成已经逐项演示所有建筑制作环节。

## 2. 当前实现与真实缺口

| 当前能力 | 代码证据 | 应补齐的部分 |
|---|---|---|
| 资源浏览、Property 编解码、语义类型 | `crates/sc-properties`；`src-tauri/src/package_service.rs` | 将单资源信息连接成可编辑关系会话 |
| 模型引用解析 | `src-tauri/src/prop_models.rs` | 模型专用解析不能代替菜单、Locale、图片的通用来源解析 |
| 菜单复刻及实时草稿 | `src/stores/uiWorkbench.ts`；`src/pages/studio/panels/ui.vue` | 使用当前安装的原始 Property 驱动，而非仅消费静态提取的展示数据 |
| 页面导出 | `MenuEditorPanel.vue:onExport` | 当前复制 `exportSchema()` JSON；接入构建、校验与验证记录 |
| 现有 Property 补丁 | `package_service.rs:apply_property_patches/patch_property_overlay` | 可修改已有标量和等长数组；增加受约束的新资源身份及多资源事务 |
| DBPF writer | `crates/dbpf/src/writer.rs` | 可写多资源，不能把其成功返回当成语义闭包通过 |
| 加载路径研究 | `package-runtime-verification-20261017.md` | 将实际命中源验证关联到每次构建产物 |

源码中还存在 `menu-export.ts` 与 `buildGameExport()`，因此“完全没有 package 导出代码”不准确。不过当前页面没有调用它们，且不能直接接上线：

1. `buildGameExport()` 遍历 `category.items`，没有合并 `added`、没有排除 `removed`，也没有对原条目应用 `applyEdit`；编辑标记会触发导出，但写入的名称、图片、排序仍可能是原值。
2. `buildMenuPropertyResource()` 从少量展示字段重建 Property，固定 Group `09878A01`、继承 Parent `AF042E9A`。对 Menu2 或其他模板会改错身份/继承，并丢掉原功能字段与未知字段。
3. `replicaToolToWorkbench()` 将排序重建成 10/20/30，不能拿这个显示位置覆盖原 `uiPosition` 而不告知用户。
4. 生成器无条件写 marquee Key，即使本次没有图片且目标不存在；自定义分类 `NEW-CAT-*` 也不是可直接 parseInt 的游戏 ID。
5. `0x0975695F` 在原 C# 菜单复制中用作 `menuUnit`，导出器却作为 `hardGate` 按 locked 布尔值生成引用。语义需按模板/类型确认，不得把锁定显示状态直接编译成这个字段。
6. Locale 导出只写改动字符串，却复用官方表 TGI。现有证据没有证明引擎会按字符串合并多个同 TGI 表；可能替换整表，也可能被更高优先级 Locale 包遮蔽。
7. `buildMenuExport()` 对空 entries 仍读取第一项；原始快照、冲突、外部依赖和游戏验收记录均未纳入构建。

这些是代码路径审查发现，未在本轮逐项运行故障复现。应把展示草稿与游戏可写文档分开，新增基于原资源的编译路径，不能仅为旧导出按钮加一条调用。

## 3. 关联如何成为编辑器的核心

最小关系视图以所选菜单条目为中心，默认显示归属菜单、图标、大图、名称/描述、执行对象；展开执行对象才显示 Unit/Network、显示模型、Lot、LOD、材质等。无需先画出整个安装的资源图。

每条关系保存：源完整 TGI、字段 hash、数组下标、原 Key/Text 值、解析规则、目标完整 TGI、候选包、编辑器选定源及运行时命中状态。显示“来自本项/继承自模板”“由几项共享”“缺失/歧义/项目覆盖”。同 Instance 不代表同资源；Type/Group 为零的语义引用不能用任意首个同 Instance 匹配。

建立两个不同的边：

- Property 继承边：`0x00B2CCCB`，只读展开时保留来源，不自动展平保存。
- 菜单归属边：`0x0DB9FC63` 数组，支撑移动、增加归属与复制入口。

图标 `0x0977AA8F`、大图 `0x0DDEEE56`、标题 `0x0A09F5FA`、描述 `0x0A09F5FB`、排序 `0x0DC1E3E0` 可作为首批有证据的字段；是否本地存在、继承、标量或数组仍按原文件读取。不可写字段要明确显示原因。

建议后端会话保存源包路径/哈希、资源 payload 哈希、完整 Property、解析后的关系、操作列表、固定的 ID 分配表。前端仅提交 `moveMembership`、`duplicateEntry`、`replaceIcon`、`editText` 等语义操作，字段规则由后端统一验证。

交互流程：选择游戏项 → 自动展示关联资源 → 编辑并即时预览 → 查看受影响资源 → 构建/重读 → 安装验证 → 返回同一项目查看结果。资源浏览器上的 Property Key 可跳转目标；也能从图片反查引用它的菜单项。

## 4. 分阶段实现，不把后续能力设为前置条件

### A. 复现移动入口

从当前安装确认路径条目及道路归属；完整读取原始 Property，仅改 `0x0DB9FC63` 的选定元素，保留 Type/Group/Instance、继承和其余所有字段。现有等长数组补丁适合该案例。若字段继承或缺失，不修改共享父模板；支持本地 override 前先明确标记该样本不适用。

输出一条 Property 的 overlay。源资源更新时以 payload 哈希检测冲突，禁止覆盖旧草稿假设。预览使用“原始文档 + 操作”与构建器相同的有效模型，避免屏幕和产物各写一套规则。

### B. 保留原项并复制入口

复制完整 Property，保留原 Type/Group，分配新的 Instance，修改复制项的归属；图标、文本、Network/Unit 仍引用原资源。新增 TGI 需检查项目与已索引安装的冲突，检查菜单枚举/消费机制，不等同于修改某个 UI 数组。

ID 分配应持久化到项目，不随名称变更；哈希/随机生成只是候选，还要检查冲突和该家族的身份约束。首次重新导出必须得到同一身份。

验收：大学原项仍在，道路新增项可见，而且两者均能选择并实际绘制路径。**入口复制不等待 RW4 writer、Unit 深克隆或通用数组编辑器。**

### C. 修改图标与信息

默认“仅当前入口”：新增图像资源，重写所选条目的 Key；保留共享原图，避免顺带影响其他建筑。读取实际尺寸、格式及状态图关系，常见 128×128 PNG、454×263 JPEG 作为有样本支持的预设，不作为所有菜单的硬编码规则。将“修改所有引用者”作为明确不同操作。

文字按 Text 的 table/string 引用编辑，默认独立字符串身份。先验证自建表是否可解析及其语言选择规则；可行则用项目私有表，不能直接往官方表 TGI 写一张仅含变更项的表。若必须覆盖官方表，则合并完整有效表，明确冲突和优先级，再做其他菜单文字未丢失的回归验证。

OpenSCP 自身标签、错误、状态和无障碍文本全部同步 zh-CN/en-US；mod 文案按目标游戏语言分别保存。应用语言切换与游戏语言切换是两个验收维度。

### D. 独立建筑变体

在入口闭环后，从已存在建筑复制 Unit/Lot 等需要独立编辑的节点；未改变的模型/纹理可以继续共享。通过复制映射统一重写引用，并标出仍共享的依赖。原 C# `mnuCopy_Click` 提供参考，不能代替完整依赖分析。

“新增一个建筑菜单入口”“独立建筑变体”“从外部模型制作全新建筑”是三个能力层次。前两者不必等待任意模型编译；第三者才需要对应模型/材质写回与游戏行为配置。造价和维护费应追踪真实来源，当前尚未解析不代表原则上无法编辑。

## 5. package 完整性与游戏验证链

构建器生成最小变更资源集合和外部依赖清单，外部引用允许明确依赖基础游戏/DLC，不能以“没有全部复制进包”为断链。缺失、歧义、类型错误、循环继承、身份冲突和不支持操作必须定位到具体关系/字段。

| 层级 | 检查与结果 | 不能替代什么 |
|---|---|---|
| 文档 | 原始快照、操作和最终模型一致；未编辑字段保持语义相同 | 游戏是否读取 |
| 二进制 | 重开包、重解析每条资源、比较 TGI/类型/数组/引用；检查重复 TGI、越界、索引 size 标志及长度 | 引擎格式兼容 |
| 准入/注册 | 实机 Packed Open、RegisterDatabase 成功 | 目标资源是否来自本包 |
| 实际命中 | 观察目标 TGI 的最终来源，记录路径、priority、注册顺序与 materialize | 菜单可见/功能正确 |
| UI 与功能 | 对照截图、hover、文字/图标、归属、点击和绘制/放置行为 | 存读档与移除后的恢复 |
| 回归 | 重启仍生效；移除本次包后恢复基线；建筑变体再测测试城市存读档 | 不同游戏构建的兼容性 |

已有单 TGI 实验与多条包 Open 修复证明底座已有实际进展，无需重新从“能否加载 package”开始。但也不能将它们标成菜单行为已通过。

安装验证绑定实际运行 EXE 和安装目录，不拿浏览器中另一个游戏目录代替。现有实验证明 UserData/Packages 注册成功仍可输给 Data 的同 TGI；文件名前缀也不是通用优先级规则。首次普通 overlay 验证走重启，所见即所得先指编辑器内即时反馈与可靠对拍，不承诺运行中热重载。

每次验证留存：构建 ID、源与产物 SHA-256、游戏 EXE 哈希、TGI/字段差异、安装位置、运行时命中事件、前后截图、操作结果和恢复结果。记录“未验证/通过/失败”的具体阶段，不能只有一个绿色“成功”。临时部署按产物哈希恢复，仅处理本项目安装的文件。

## 6. 首个可交付切片与测试

首个切片包含 A+B：真实菜单会话、两类关系、移动/复制操作、一个共享编译器、包重读、安装验证记录。入口至少支持资源浏览器中的菜单 Property 打开工作台；已有复刻工作台复用渲染和图片裁切，不另建一个只有演示数据的页面。

建议新增 `src-tauri/src/menu_editing.rs` 编排会话/操作/构建；Property/关系纯逻辑留在 Rust crate，DBPF 容器继续用现有 writer。`src/stores/uiWorkbench.ts` 接真实会话；`MenuEditorPanel.vue` 接构建报告与验证结果。接口名称和文件划分是设计建议，尚未实现。

必要测试：

1. 用真实样本的脱敏/可分发 fixture 验证归属数组单元素替换，继承 Parent、其他元素、Network/Unit、未知字段不变。
2. 复制入口只产生一个新 Property，原资源不变；冲突分配、稳定重导出、缺失依赖和继承循环有确定结果。
3. UI 修改后的文案/图标/排序进入同一个构建模型；新增、移除与空项目没有旧导出器的遗漏或崩溃。基础包资源的“删除”不能通过 overlay 不包含它来实现，未定义隐藏机制前不宣称支持。
4. 图标更换不影响共享原图；Locale 测试覆盖中英文、表合并/私有表与无关字符串保留。
5. 多条资源索引按游戏读取规则验证，不能只靠同源 writer/parser 自证；沿用已有 sizeflag 回归测试。
6. 游戏基线 → 移动 → 复制 → 移除恢复。移动时大学消失/道路出现；复制时两处均在；两次均验证路径实际可绘制。

完成标准是用户无需手记 TGI、切换多个工具或手工拼包，能从一个菜单条目完成修改并追溯游戏验证结果。A+B 完成后，再把图片和文字加入相同事务，从这个局部闭环扩展到建筑编辑。

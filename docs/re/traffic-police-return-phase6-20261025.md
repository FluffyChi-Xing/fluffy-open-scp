## 结论

现有日志已经足以证明警车的交通任务是由 transaction 驱动的状态链，而不是每辆车各自输出一条完整的“寻路日志”。对本次样本可以稳定使用以下解释：

| 观测 | 当前解释 | 证据强度 |
|---|---|---|
| `current sink = 323` | 实际选择犯罪进行中的目标（`CrimeInProgress`） | 已由脚本表和触发式采样闭合 |
| `current sink = 1122` | 巡逻点目标（`PatrolPoint`） | 已由脚本表闭合 |
| `323 → 1122` | 到达犯罪目标后没有完成捕获，或目标已被其他警车处理，任务恢复巡逻 | 强推断；有 9 次同身份转移，附近没有对应的捕获资源变化 |
| `323 → 109` | 高度疑似捕获后进入返回/押送相关任务 | 强推断；两次同 Agent、同 key、同 handler 转移均随后出现捕获和入狱资源变化 |
| `109` 的精确脚本名 | 尚未闭合 | 未知 |
| `708` | 车库出发、派车或巡逻任务的中间 sink | 强推断；在三倍速样本中反复出现在 `708/1122` 与犯罪目标切换之前 |

`109` 不能单独等同于“正在押送罪犯”：它在普通交通窗口也大量出现。因此必须使用“同一 handler + transaction key + Agent 地址 + 位置连续性”，并用资源事件确认捕获，不能只按 sink 数量下结论。

## 两条最强的抓捕闭环

`alignment-phase6.json` 中有 697 次同身份 sink 转移，其中和犯罪目标有关的计数为：

| 转移 | 次数 | 同身份保留 | 距离统计 |
|---|---:|---:|---:|
| `1122 → 323` | 3 | 3 | 中位约 7.6 |
| `323 → 1122` | 9 | 9 | 中位约 137.0 |
| `323 → 109` | 2 | 2 | 中位约 444.5 |

两条 `323 → 109` 记录如下：

1. `transaction key=12993`，Agent `0xbc315e54`，`simTick 80849 → 80850`。位置完全不变，路径前缀仍相同；`80855`（+5 tick）出现 `CriminalsArrested +1`、`CriminalsAtLarge -1`、`TradeTrackingCriminalsCaught +1`；`80887`（+37 tick）出现 `CriminalsIncarcerated +1`。
2. `transaction key=15784`，Agent `0x9a70fd54`，`simTick 81194 → 81195`。`81200`（+5 tick）和 `81202`（+7 tick）出现捕获资源变化；`81228`（+33 tick）及之后出现 `CriminalsIncarcerated +1`。

这两组样本同时满足状态转移、身份连续、时间顺序和资源结果四个条件，是目前“警车抵达犯罪目标后转入押送/返回阶段”的最强运行时证据。它们不能单独证明 `109` 就是监狱 sink，因为 `109` 的名称仍未从脚本表直接闭合。

## 未命中与恢复巡逻

同一对齐窗口出现 9 次同身份 `323 → 1122`，但相应转移附近没有捕获资源增加。静态规则明确规定：警车抵达后如果 `Criminal` 数量为 0，会清除 `CrimeInProgress` 并回到返回 Maxis Man 的链；这与“警情已被其他警车处理、罪犯已离开，或采样时刻没有命中活动目标”相容。

因此用户观察到的三种行为可以在日志层面初步分为：

1. **巡逻中**：`1122`，并伴随持续移动或道路段变化。
2. **出警/处理警情**：`1122 → 323`，之后保持 `323` 并沿新的路径段移动。
3. **到达后未捕获**：`323 → 1122`，没有捕获资源变化。
4. **捕获后返回/押送候选**：`323 → 109`，随后出现捕获资源变化，再晚一些出现入狱资源变化。

静态规则也解释了为什么流程不是固定的“抓到后一定送监狱”：捕获链会先消耗 `Criminal`、犯罪类型和 `PoliceOutreach`，增加 `CriminalsArrested` 与 `TradeTrackingCriminalsCaught`，减少 `CriminalsAtLarge`；只有监狱有空位时才在 `DepositAtJail` 中增加 `CriminalsIncarcerated`，满员时会走另一条处理链。

## 并发警情与三倍速样本

在并发窗口 `simTick=74607`，同时看到 5 辆车的当前 sink 为 `323`、6 辆为 `1122`、2 辆为 `109`。5 辆 `323` 车辆至少分成两个空间簇：一簇在约 `x=895`、`y=-520~-820`，另一辆在约 `(-850,-654)`。这支持多个警情或多个并行警务 transaction 同时存在；它不能单独证明恰好对应三个罪犯。

三倍速窗口共观察 412 个 tick 行、6,567 个车辆节点观察。触发 tick `74128` 同时有 6 辆 `PatrolCar` 选择 `323`。其中 key `2400` 的同地址链在触发附近为：

```text
708 → 1122 → 708 → 1122 → 708 → 323 → 109
```

`323` 出现在 `74128`，下一次观察 `74129` 转为 `109`，Agent 地址仍为 `0x4fac2664`，handler 和 key 也保持一致。此前反复出现的 `708/1122` 更像任务准备、巡逻目标或中间路由状态；采样未能把 `708` 的确切脚本名闭合。

三倍速数据还显示 76 个缺失 tick 和 6,313 次读取错误。它适合证明并发和状态转移存在，不适合做精确的城市级事件总量估计。

## 日志到底记录了什么

探针实际能看到的是交通状态快照：

- `PatrolCar` 的 TransportEntry index `50`；
- handler、transaction key、Agent 地址；
- 当前 sink 和候选 sink 列表；
- 位置、速度、路径段字段，以及路径重算剩余时间和停止时间；
- 资源状态变化，如捕获、在逃和入狱数量。

它没有看到一条现成的“警车从 A 到 B，采用道路段 X/Y/Z”的游戏日志。当前可复原的寻路证据是：sink 发生改变、位置连续变化、路径段字段变化，以及同一 Agent 的速度和停留状态变化。候选列表例如 `[323,1122,109,5]` 只表示任务可能使用的分支，不能当作已经执行过的路线。

Agent 地址会复用，transaction key 也会复用；因此单独按 key 或单独按地址统计会把不同车辆或不同任务拼在一起。现有分析使用三元身份（handler、key、Agent 地址），并在必要时对位置连续性做校验。

## 对车辆池和资源运输问题的含义

本批日志支持“多个警车可以并发运行”以及“车辆 Agent 会释放/复用”，但还不能回答“80 辆警车是否全部存在于一个可见对象池”或“全局 6000 上限是否已经造成运输资源饥饿”。源码里的 `mMaximumVehicles=6000` 只是配置上限，不是当前已分配数量，也不是警车专用上限。

目前能确认的运行时量级是：普通全车辆窗口每次快照约 1,454 个有效 Agent，峰值 3,463；修正后的警车窗口每次约 25 个道路活动 `PatrolCar` Agent，非零速度约 12 个。警车窗口只代表当前出现在交通 Agent 集合中的车辆，不包括车库、等待派车或服务系统内部的车辆。

因此，现有证据更支持“警务系统按事件和 transaction 调度可见车辆，多个案件可同时占用车辆”，尚不足以支持“达到代理池上限导致货物/资源没有 agent 运输”的结论。要证明池耗尽，必须同时出现：新 transaction 创建失败或长期等待、Agent 地址复用/回收率显著上升、警务和普通运输的失败率同步上升，并且这些现象与接近车辆上限的运行时计数相互对齐。

## 最终判断

对于已经捕获的几十轮样本，答案是：**可以分离出巡逻、出警、未命中恢复和捕获后返回候选四类状态；其中两条 `323→109→捕获资源→入狱资源` 链已经形成强闭环。** 目前仍缺少 `109` 的精确脚本名称、单辆车与单个罪犯的一对一绑定、监狱路径的逐段道路映射，以及车辆总库存/对象池上限的运行时计数。

后续若重新进行实验，最高价值的目标是闭合 `109` 和 `708` 的脚本名，并同时读取警察局停车/等待派车资源；不需要再做大范围盲目截图或短时间随机捕获。

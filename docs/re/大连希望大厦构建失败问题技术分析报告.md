# 大连希望大厦构建失败问题技术分析报告

日期：2026-11-08  
范围：只读分析当前 `asset_build_m1` 构建器、s31 大学样本与大连希望大厦样本；不修改代码、不宣称已完成游戏内运行验证。

## 结论摘要

大连希望大厦的失败不是 DBPF 容器写坏，也不是“模型太复杂所以随机崩”。真正的问题是：当前构建器把一条“从零菜单 + 新模型物化”的资产路线当成了已满足游戏契约的成功路线，但它只完成了资源写出和局部菜单链接，没有把模型材质输入、放置边界、Unit 行为类别和运行时依赖闭合为一个可被游戏完整解释的建筑。

s31 能反复成功，是因为它走的是“成熟 donor 建筑的属性/行为重写”路线：参照 Unit、Lot、路径、教育模板、bundle、菜单统计和图标均来自已经被游戏消费过的链条；构建器主要做字段覆盖和场景 lowering。希望大厦则走 from-zero 菜单路线，场景/模型是主要事实来源，构建器必须推导并生成更多原生资源；目前该推导链仍允许带警告产包，导致“构建成功”与“游戏可用”脱钩。

## 2. 两条构建路线的本质差异

### 2.0 先排除插件和 LOTM 源文件

本次以 `D:\ea-games\simcity_offline\entity\SC5 Asset Editor 1.23.7\ny_facade` 为金样本；没有修改、修复或重新解释该插件。插件 `native_asset.py` 的 v9 写入顺序是
`(empty, normal, empty, empty, tint, palette, shader, interior)`，并追加 4×float4 参数表。
后端 `asset_build_m1::lotm` 的读取常量和 `materials::resolve_one` 的映射与此顺序一致。

对实际文件的只读结构对拍如下：

| 文件 | v9 mesh/material | 每材质容器槽 | params | mesh uv_kind | SHA-256（前 16 位） |
|---|---:|---:|---:|---:|---|
| `tmp/final/Institute.plugin.lotm`（大学插件金样本） | 74/74 | 8 | 64 bytes, 1 列 | 2 | `1dbbc4f327a3ed98` |
| `tmp/hope-project/...954cbf.lotm`（希望实际输入） | 66/66 | 8 | 64 bytes, 1 列 | 2 | `876d7c56b59a7b19` |

希望 LOTM 的每个材质均有非空槽：index 1=normal、4=tint、5=palette、6=shader、7=interior；index 0/2/3 为空是插件协议设计，不是丢失。故“希望源 LOTM 没有六槽语义”不成立；语义是在后端输出 RW4/材质绑定阶段被压扁或未被验证。

### s31：donor/overlay 路线

`m1.s31.json` 指向已有大学 Lot `00B1B104:40E1C000:BE18DA2D`，并提供 `presentation-donor.package`。账本显示：

- `menuMode=false`，没有从零生成的新菜单身份；
- `loweredUnits=49`，场景单元被写回参照 Lot；
- `insert-model` 关闭材质缓存且没有新增材质资源；
- `behavior-bind` 复用教育模板 `0x7E4B99E5` 和完整 bundle 并集，且写入教育类别、lot board、统计行、图标等；
- `menu-contract` 虽提示“公园面板 + 非公园 Unit 类别”的待核验组合，但资源链仍以成熟教育建筑为骨架。

这条路线的错误半径小：即使某个设计值不理想，游戏仍能找到原生模型、原生材质、原生 PathEntry、模板 bundle 和已注册的 Unit 形状。

### 希望大厦：from-zero menu + model route

`m1.hope-tower.json` 只有一个 `reference.lot`，另有新 LOTM 和菜单图像；六个 `texture-input-*` 节点的 `config.asset` 全为空。账本显示：

- `menuMode=true`，`menu_instance=0x3CAAEFBB`，构建器生成新的 Menu2/Unit/Lot/locale/icon/marquee 身份；
- `loweredUnits=0`，29 个场景单元没有按 donor/derived Lot 方式 lowering；
- `insert-textures.slots=0`，但 `insert-model` 仍编译出 66 个 mesh、66 个材质组、119 个材质资源；六槽指纹为全零实例；
- `property-patches=0`，行为不是对已有完整 Unit 的受控 patch，而是依赖菜单语义和模板绑定补齐；
- `menu-contract` 明确记录 `00F9EFBA BoundingBox missing` 和 `Unit behavior category missing`；
- `delta-audit` 因“no identity donor lot”跳过 menu identity 对拍，不能证明新身份与原生菜单契约等价。

账本中的 `modelShape` 指纹为 `null`。`package.rs` 在这种情况下使用 `doc.meshes.len()>4` 的 `safe_nh` 分支，等价于 `nh-partitioned`：所有 mesh 的 material row 被归零，只保留 dominant/head 材质的六个实例。希望 LOTM 虽有 66 个独立材质，最终模型却只使用一个头材质；其余 118 个材质资源仅被写入资源池，未必被模型引用。这是当前后端把“多材质原生输入”错误降级为“单材质 NH 模型”的确定性信息损失点。

这不是“资源少一点”的差异，而是解释器输入层级不同：s31 输入的是已闭合的游戏资产图，hope 输入的是模型 + 部分语义，构建器却输出了看似完整的 package。

## 3. 已证实的构建器问题

### 3.1 外部六槽为空与 LOTM 六槽混为一谈

`hope` 的六个 `texture-input-*` 节点都没有绑定资源，账本却出现 119 个材质资源和 66 个材质组。`textureSlotInstances=[0,0,0,0,0,0]`、`slotPayloadSha256=e3b0...b855` 只描述 schema 外部槽位，不描述 LOTM 内每材质槽；当前闸门把两者放进同一指纹，造成“外部槽为空”与“LOTM 源材质存在”无法区分。

对游戏而言，材质资源存在不代表 shader 所需的 slot0–slot5 语义存在。工作台的 GLB 预览可以依靠编辑器路径或烘焙顶点色显示；游戏的 building4 链需要原生 raster/RW4 资源、TANGENT、参数列和正确的槽位引用。当前账本只能证明“编译器写了资源”，不能证明“模型的每个材质引用在游戏 ResourceMan 中可解析”。

### 3.2 多材质模型被自动压成单材质

`package.rs` 的 `safe_nh` 规则以 mesh 数量触发，并把 `mesh_material` 全部置零；这解释了希望塔为何会“几何存在但外观完全错/白模”，也解释了大学 s31 为什么不能作为同类对照：s31 ledger 的 `insert-model` 没有模型合同、没有新增材质资源，它直接复用了 donor 模型。

### 3.3 BoundingBox 缺失被降级为 warning

`menu_contract.rs` 对 `0x00F9EFBA` 缺失只发 warning。反编译源码中，Lot 的放置边界参与 `cToolPlop::UnitAtValidLocation`、UnitLot transform、pipe/sink 邻接和地图/碰撞范围。缺失时游戏可能采用极小默认值、错误脚印或在放置后无法建立连接；这类错误不会必然在 DBPF 打开阶段暴露，却会表现为建筑不渲染、不可连接、详情绑定为空或放置后被规则清除。

因此 BoundingBox 对新建筑不是可选美化字段，而是放置契约字段。希望大厦当前“包能写出”掩盖了“建筑没有可验证放置体积”。

### 3.4 Unit behavior category 缺失仍允许生成菜单

希望大厦的菜单语义声明了 `buildingCategoryInstance=0xC710B6E9`，但 ledger 的 `menu-contract` 仍报告 Unit behavior category missing。这说明 Menu2 的 UI category、Unit 的 `0x0AFE27B1` 行为类别和 Lot board/placement family 没有形成一致三元组。

反编译的 EcoGame 初始化会按主表扫描 Unit group，构造 `cEcoUnitEntry`，再由 bundle/规则建立模拟实体；菜单只是入口，不会替 Unit 补行为。没有行为类别或有效 bundle 时，菜单可以出现，但放置后的 cEcoUnit 可能没有正确的资源 bin、规则集或 UI 查询对象。

### 3.5 from-zero 路径缺少 fail-closed 依赖闭包

希望大厦的 `delta-audit` 记录“no identity donor lot (from-zero menu route)”并跳过身份对拍。构建器对新菜单身份采用确定性 instance 和线性探测是合理的，但当前验证只检查输出内部链接，不检查：

1. Unit 的 parent/template、behavior category、bundle 并集是否可在已注册脚本库解析；
2. Lot 的 BoundingBox、LotMask、model/LOD、PathEntry 是否完整；
3. Menu2 的 parent、uiCategories、building category、统计行、locale、icon/marquee 是否满足同一原生菜单族；
4. 新模型所有 material/TANGENT/slot 引用是否能跨包解析；
5. same-TGI 或外部 package priority 是否会遮蔽新资源。

这就是“构建器在 s31 上可靠，在 hope 上完全崩坏”的根因：它对 donor 路线验证的是差分，对 from-zero 路线验证的是文件存在性。

## 4. 游戏运行时为什么会放大这些缺口

反编译源码表明，游戏不是一次性“验证整栋建筑”，而是分阶段、按需读取：DBPF 先注册；ResourceMan 按 TGI 首命中；EcoGame 再扫描主表声明的组并实例化 Unit/Bundle；放置时再读取 Lot 边界、路径、sink、规则和 UI board。任何后续阶段缺字段都可能静默降级，而不是在 package 注册时报错。

所以 hope 的 137 条资源能通过构建器回读，并不能证明它能完成“菜单入口 → Unit → Lot → model/material → EcoGame behavior → placement/UI”的闭环。

## 5. 解释器层的真正缺口：IR 意图没有被编译成资产路线

用户 IR 不应该要求用户填写 `nh-atlas`、`native-multi` 或 RW4 细节；这些是游戏侧实现策略。当前代码已经尝试把缺省 `modelShape` 固化为 `nh-atlas`，但这只是把一次 UI 漏填变成另一个硬编码选择，并没有完成解释器职责。

从现有代码和测试可以确定三件事：

1. `lower_schema()` 把 `scene.modelShape` 变成实现路线；`package.rs` 又用 `doc.meshes.len()>4` 的 `safe_nh` 覆盖该意图，存在两套相互竞争的路线选择器。
2. `nh-atlas` 的语义是“所有材质烘焙到一个 tint atlas，再以一个 head material 渲染”；`native-multi` 才是“保留 LOTM 材质组”；`nh-multimaterial` 只保留最多四组。这些都不是同一个语义的无损实现。
3. 当前 `cargo test -p fluffy-open-scp asset_build_m1 --lib` 结果为 **138 passed / 5 failed / 21 ignored**。失败中包含 LOTM 多 mesh 夹具对编译结果的结构断言，以及新菜单 lot 类型门禁与旧夹具冲突，说明路线选择和 golden fixture 已经不同步，不能继续把“全绿测试”当成解释器已稳定。

应建立单一的内部 `GeometryRoute` 推导器，输入只来自 IR 与 LOTM/场景事实，输出路线及理由：

| 输入事实 | 可推导结论 | 允许的实现路线 |
|---|---|---|
| 无 LOTM 材质、只有 plain GLB/外部槽 | 外部六槽是唯一材质来源 | schema-slot route；缺槽必须明确为空或继承 donor |
| LOTM 单材质，mesh 数量在模板上限内 | 六槽可直接绑定，材质无损 | generic/NH single route |
| LOTM 多材质且每 mesh 有有效 material ref | 必须保留材质关系 | `native-multi`、`nh-multimaterial` 或显式 atlas；不能自动归零 |
| 多材质超过游戏模型 mesh 上限 | 需要有损压缩或烘焙 | 仅当 atlas/压缩策略有可验证证据时选择，否则 fail-closed |
| LOTM diagnostics/source 标记为插件原生 | 保留插件的 UV/TANGENT/六槽协议 | 以插件字段为金样本对拍，不得退回 PBR/外部槽猜测 |

这意味着后端的正确行为不是“用户补更多字段”，而是：读取 LOTM 的材质计数、mesh-material 绑定、UV/TANGENT 声明、params 列数和来源诊断；选择一条可证明的游戏路线；在无法无损解释时拒绝构建并指出缺失的游戏侧事实。

## 6. 当前阻碍与优先级

只要 `GeometryRoute`、材质语义和 from-zero 身份闭包还没有统一，继续投入行为绑定或场景编排都会被反复回归打断。行为/场景层应该消费“已经闭合的资产图”，而不是再次猜测模型路线。优先级应是：路线推导器 → 编码产物绑定闭包 → from-zero 菜单/lot/unit 闭包 → 再扩大行为节点和场景编排覆盖。

## 7. 已实施的后端解释器修正

本轮已在后端实施第一阶段修正，插件 `ny_facade` 保持不变：

1. 新增 `asset_build_m1::geometry_route::GeometryRoute`，在 LOTM 已解析事实（材质组数、mesh 数）上统一推导路线；缺省 IR 不再被硬编码成 `nh-atlas`，`package.rs` 也不再用 `mesh_count > 4` 另起一套 `safe_nh` 覆盖路线。
2. 路线推导结果写入 `insert-model` ledger，并进入材质缓存指纹，避免不同游戏路线复用同一个缓存。
3. 插件原生多材质 LOTM（UV2、params、六槽和 mesh-material 关系完整）固定走 `native-multi`；只有非插件原生输入才按实际材质关系选择 `nh-multimaterial`/`nh-atlas`。显式 `modelShape` 仍保留为旧 schema 的兼容逃生口。
4. 新增 `material-binding-contract`，在编码后的 RW4 MATERIAL 行上检查 raster 是否存在且不是空壳，防止“资源数量很多但模型引用白色空 raster”的构建假成功。
5. 新身份菜单参照 lot 类型已收紧为 `58F0C000` lot-config；`40E1C000` 只保留给 donor 身份克隆路线。参照 lot 的主体列（BoundingBox、LotSize、LotMask）缺失时 fail-closed，并记录继承链。

真实三样本回归已补齐：商业建筑 98 mesh/98 binding，大学 71/71，希望大厦 66/66；三者均走插件原生 `native-multi`，每个输出 mesh 都有材质绑定。希望样本的参考 lot 已纠正为参考包实际存在的 `00B1B104:58F0C000:2063CCDD`。本轮还修复了普通菜单路线未写 `0x0AFE27B1` Unit 行为类别的问题；该字段由后端根据语义补齐，不要求用户在 UI 中填写。

离线回归夹具也已迁移到真实契约：严格菜单测试的 LotMask 现在带可解析 1×1 raster；黄金 fixture 在边界处把历史错误组的 `593B61D2` 模板和 `8D007745` lot 规范化到 `48E0C000`/`58F0C000`。`cargo test -p fluffy-open-scp asset_build_m1 --lib` 当前为 148 passed、0 failed、22 ignored。游戏启动和冷启动 oracle 尚未执行，按规则由用户手动完成。

Asset Editor 的 `editor.workbench.menu.enabled` 已从构建判定中移除。它不是用户语义，也不是 UI 可配置开关；只要菜单对象包含有效标题、类别、父级或成本等作者配置，解释器就保留并编译其 JSON 原值。没有菜单对象才跳过菜单阶段。大学 s31 的手工 schema/行为链不经过该规则。

商业地标工程没有 `openscp.asset` schema，后端现已增加受限适配器：一键构建优先使用已有 M1 schema（因此大学路径不变），只有缺 schema 且存在 `asset.lot.json` 时才读取 Asset Editor workbench。适配器解析 LOTM、场景写入、菜单和逻辑节点，解析 sourceLot 的真实游戏包，并从包内选择 `58F0C000` lot-config 作为新菜单 donor；不会把 `41F0C000` asset-dictionary 当作 donor。源包会复制为项目内 `build/reference.package`，已有副本若哈希/字节不一致则拒绝复用。缺源包或缺 lot-config 时 fail-closed，不伪造 TGI。

首次无头实构建又暴露出两个真实 Asset Editor 输入差异：商业节点同时写 tourism/park attraction，解释器现以 tourism 为权威并保留 park 的地价语义；菜单图标虽名为 `.png` 实际是 JPEG，菜单图标在内存中转码为 PNG，不改作者文件；rollover 的 `.png` 字段在存在同名 `.jpg` 时归一到 `.jpg`。临时根构建结果：商业 `1914` resources、32 units、1 path，SHA-256 `2a4aa93f63f90a9cdc8a0c635baa35a00aaa17dacf68b2eee6f1edfe1235b27f`；希望 `148` resources、29 units、2 paths，SHA-256 `a8ee0e77f01a2d8fd817b7470cc166ba4b83b41cd881f60b008f4ee9533fe884`。这些包尚未部署到游戏。

这组改动的目标是让后端成为 IR 到游戏资产图的解释器，而不是把 UI 字段原样搬运到 DBPF。当前验证结果为：GeometryRoute 单元测试、工作台 LOTM 全 mesh/material 回归和菜单 lot-mask 闭包测试通过；完整 M1 测试仍有黄金 fixture 缺少新身份路线通用模板的既有失败，详见第 9 节。

## 8. 后续准确修正方向

1. **LOTM 与 schema 槽位分层**：LOTM 内部六槽完整时，不得因 `scene.slots` 为空而把材质判为零；外部槽位只用于 plain-GLB/显式覆盖路线。
2. **多材质路线禁止静默归零**：66 material 的 LOTM 不得自动进入 `safe_nh` 单材质分支；无法推导无损路线时必须 fail-closed。
3. **分离三种成功**：`container-valid`、`resource-graph-valid`、`runtime-contract-ready`。
4. **from-zero 菜单契约 fail-closed**：BoundingBox、Unit behavior category、模板/bundle、LOD/PathEntry 和 locale/resource priority 闭包缺一不可。
5. **将游戏冷启动菜单作为 cheap acceptance test**：卡菜单即停止后续进城、放置和存档步骤。

## 9. 证据边界

本报告已证实构建器账本差异和源码层依赖；没有把“希望大厦在游戏内的具体画面症状”伪装成静态证据。要把某一症状归因到材质、BoundingBox、Unit bundle 或菜单家族，仍需在隔离城市中按用户规定做冷启动/运行时 probe，并先核对 `test-archive/MANIFEST.md` 与 SHA-256。

# OpenSCP 行为叶子的核心接线与 bin 冲突

## 引擎怎样处理重叠

1. **声明会合并。** Unit 的 core 先处理。随后 `cEcoUnitEntry::FillFromProps` 按 A2 → A5 的顺序查 bundle，B2 按 instance 排除。普通 bundle 遇到已有的 resource index 时，`GB::FillFromProps` 复用本地 bin，并分别以较大值合并声明容量和显式初值。声明两次同一个 bin 不会提供两套库存，也不会把两个容量相加。
2. **绑定会覆盖。** 每个普通 bundle 加载末尾调用 `AddBundlePropOverrides`。若有效 Unit Float 和目标 bin 均存在，就按倍率直接写容量或初值。初值还可能反向计算并钳制。下一 bundle 的声明又可能抬高容量，再由自己的绑定改写。因此需要按原版顺序重放声明及覆盖，单看原始容量和交集无法预测最终结果。
3. **接收行单独注册。** `AddBundle` 为每条可解析的 sink 行追加记录，保存 sink entry、规则和可选 key resource。`AddUnitSinks` 将记录逐项交给 transport handler，交付检查按具体 slot 取规则。因此同一个 sink ID 可以带不同规则进入候选。已确认两个候选会被注册的代码路径，具体谁获得一次交付由接入、测试和寻路决定。

上述分支在零售反编译 `SimCity.unwrapped.exe.c:700164`、`:700292`、`:701828`、`:695679`、`:699437` 对照。带符号函数树可直接查看 `GB/FillFromProps.c:83`、`GB/cEcoUnitEntry/AddBundlePropOverrides.c:85`、`GB/cEcoUnitEntry/AddBundle.c:416`、`GB/cEcoGame/AddUnitSinks.c:64` 和 `GB/cEcoGame/CanDeliverTransaction.c:52`。

## 已定位的组合问题

### 住宅单叶内就能出现两个返家处理器

当前巨塔住宅先使用科潘居民经济，再用 `78A730CD/EBFC1753` 替换原入住入口。排除 `999F8484` 处理了搬入 sink `BBAAD3D1` 的二选一。另两条学生返家 sink 仍在两个 bundle 中同时出现。

| Sink | 科潘 `AB9A0A3E` | 巨塔 `EBFC1753` |
| --- | --- | --- |
| `5770FEDD` | `57537A37 → BDE74E68 → 414C4DED` | `E69F0402 → BF1AA0D6 → 9A62895D → 5E9E1700 → 57537A37` |
| `5B18518D` | `CC065767 → 414C4DED` | `DC0DE32E → 9ABD1ACA → 3BB66689 → F7A7276C → CC065767` |

巨塔入口在进入科潘通用链前还处理本地 `332C053E` 和全局 `BE2C0EB3`。后续通用链接收知识载荷并更新 `Student`。两条入口的选择会影响额外计数是否走到，属于单叶内部的真实接线差异。小学与住宅混挂还有一个声明层重叠，`Student (2C1DA112)` 在小学为 10000，在科潘基础声明为 0，并有后续住宅容量绑定。应追踪在校学生和已返家学生的读写及各自的清理时机。

### 顾客可以有意共享一池空位

原版普通 W2 商业已让 `3A8263E2` 和观光 `75D22FD1` 共享 `OpenShoppers (CE6E3D2D)`、`TotalShoppers (C1F569B9)`，用同一 `0AD6A725` 初始化空位。顾客与游客走不同入口，各自扣商品或纪念品。这个原版组合适合验证 **一池容量、不同客源**，并按一套参数配置。

公园和观光也共享两个 bin 和同一初值来源，组合时需确认各自的退场链。公园 W2 与商业另有 `6A0AC143 → 24629080`、`0992906E → 64C38F81` 两对完全相同的入口。重复注册须单列，即使两份接线 bundle 的 bin 声明没有交集。公园和住宅的选定样本还在 `790C2A95` 上分别注册 `345497CE` 与 `8A1478E7`，公园规则额外检查事务资源 `790C2A95`。公园与学校会共用 `OverCrowding (14A99156)`，公园离场链确实会消费该槽，学校分支的具体影响待验证。

### 办公、住宅与商业需要明确各自控制的参数

- **办公与住宅。** 办公 patch 将 `0A7917CB` 写成岗位合计，住宅用该列控制 `TotalResidents`、`CarW1` 等容量。两者还把同一个 `MoneyToken (54B5A6C6)` 容量映射到该列的三倍。需要独立配置人口和岗位时，原有绑定只给了一个输入。样本另有 10 个跨 bundle 的共享声明，包含三档车资源。当前 `OFFICE_CONFLICT` 已拦住组合。
- **办公与商业。** 两个抽取配方有 51 个来自不同 bundle 的同名资源、10 个重复 sink ID、7 个共同的 bin 绑定字段。办公劳工 bundle 是地面劳工 bundle 的派生版。以 sink `4D359069` 为例，办公注册 `723CEE6D`，商业注册 `B56DA4DB`。货运 `EDE0A9D3` 则两边同指 `52B15C80`。第一步是每个 Unit 明确选一个劳工 provider、一个货运入口和一份利润账本。当前 `COMMERCIAL_CONFLICT` 已拦住组合。
- **办公与观光。** 这是当前仍可走到后置 patch 的组合。原生观光写 `0C0F228C/0C0F2290 = 6/36`，办公随后把相同列写成 `9/54`。原版 `BE47F5A2` 注册 `B019AC5E`，这两列参与货运参数。这里已经能从构建顺序确定最终列值，局内货运变化仍待验证。按 `07E0AD23` 做交集不会指出这次覆盖。
- **观光与住宿。** `0E2660C6` 同时喂三档纪念品容量和 `OpenGuestsW2` 初值。此处可以没有 bin 交集，仍有参数耦合。独立调参需要独立的绑定，或者作者明确选择让两个用途共享一个值。

## 对冲突提示和配方提取的影响

现有 `behavior_conflicts.rs` 对每个叶子单独 compile，只收集 `ensure_bundles`、模板公开的 bundle 清单及两个公园补充项。它以静态目录比较资源声明、跳过同 bundle，并将同一 bin 的证据压缩成一对。办公和商业专用 patch、巨塔住宅替换、最终 donor 和排除项均在这份比较之外。

在最终 Property 的审计里，每条诊断应带上有效 bundle、来源 TGI 和消费者。优先报告三种可定位的问题。

- **多个规则绑定同一个 sink。** 记录规则 ID、特化、key resource、入口位置及优先级。首个回归样本用巨塔住宅的两个返家 sink。
- **同一字段被覆盖或同时代表两个作者参数。** 记录写入顺序、类型、最终值和读取方。首个样本用办公与观光的货运列，另加住宿共享输入。
- **资源槽共享。** 分开列出声明、初始化、运行期消费与释放。用原版零售＋W2 观光验证共享空位，用小学＋住宅验证同名学生资源的语义差异。保留原版有效组合的允许记录。

配方可从既有记录逐步提取。第一轮验证办公＋观光的最终 Property 参数、巨塔住宅的学生返家，以及普通 W2 商业＋游客共享空位。局内观察对应事务是否到达、走了哪条规则、槽值是否回到预期范围。研究阶段只读取原版包和工作区代码。

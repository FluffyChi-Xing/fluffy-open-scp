两对包分别相同。两栋主楼分别有 15 / 10 个独立车位，主楼基础岗位分别为 200/100/20、350/150/50，原生 `30645625/D07C5A04/F236BB93` 有效，但 Asset `0C12EF60=true`。因此不是“车位全丢了”或“岗位又跑到子单元了”。

已有 [停车调查](waco-office-parking-20261113.md) 证明，通勤车辆 bin 的容量是 `2147483647`，按百分比计算时，每档有少量车辆也只会请求一格。`vehicle_paths::bind/verify` 早已包含按实际数量填充的修复，但 `behavior_container_commute::route_base_staffing` 仅在发现 `building-staff` 子单元并迁回主楼后才设置 `host_parking_staff`。

新 Copan 基底编译时已经让主楼持有基础岗位（`host_base_labor`），没有可迁移的岗位子单元。这使阶段判断跳过主楼车道绑定与最终回读，留下 `true`。这是新基底路线漏接已有停车契约。

修复保留基础岗位所在位置，仅在“有作者车道、有通勤车停车道具、基础岗位已在主楼”的路线打开该契约。成品阶段另加反向闸门：这种资产如果漏开最终停车验证，直接构建失败。场景输出缓存版本升为 v20，避免回用旧产物。按实际数量显示不等于强制填满：库存不足时仍按库存显示，不伪造车辆。

## 商业：不能用盈利证明购物成功

当前瓦科与泡芙各有三档原版商场接待组件，启用 `1C1F5978/1C1F597B/1C1F597A`、`DD6E83EC/F51AB185`。原版包身份：

以 W2 为例，街道商场提供器继承地面 `3A8263E2`，success/failure 链保留：

| 阶段 | 规则 / 状态变化 |
| --- | --- |
| 取商品 | `9D3A54DC` 消耗本地 `HotItemsW2(3AB7A7C5)`；失败则 `D89831C1` 检查连接目标的同档商品 |
| 付费与购物快乐 | `2D0AB10A`，flags `02000000`：从事务扣 `MoneyToken(54B5A6C6)`，向事务写 `HappinessToken(B8928907)`，增加全城 `HappinessFromShop(E56B1F44)` |
| 商店本地结果 | 成功后 `6A449AC0` 写本地 `ProfitToken`、`HappinessFromCustomers`；这是商店状态，不是居民获得快乐的替代品 |
| 缺商品 | `CA8FFC44` 归还空位、恢复消费者事务，可继续寻店；这条路径没有经过购物快乐规则 |
| 钱不足/后续离开 | `9C34F3B9` 等离场分支处理消费者与车辆；缺钱不能通过直接补快乐绕过 |

W1/W3 对应购物快乐规则为 `2D0AB109/2D0AB10B`。这三条规则没有被自定义改写，当前提供器保留了它们；“商业节点完全没给顾客快乐 token”不符合当前静态配方。

逐规则收集属性特化并与原版三种商场有效属性对照，发现未显式复制 `0E854247=1.0`。但原始快乐输出本身就是 1；引擎 `SpecialiseUnitRule`（`SimCity-dev-ida.c:667630` 起）遇到属性缺失会跳过该次特化，保留原始规则，而非强制写 0。因此不能把这个缺项当作已证实的快乐丢失根因，更不能宣称补一个 1 就修好了挂机后的问题。

商场的客流计数和经济结算是另外的链：接待包装 `742C0A36/AAC1751E` 在基础消费完成前已经更新商场计数；现金结算也不是逐个返家居民的成功凭证。某栋商店盈利，不能证明该名居民已经买到商品、付费成功、回家交还快乐。

## 住宅端也必须接收购物结果

复用已有原版住宅规则离线证据，并从同哈希基础 AEB 核对 W1 返家链：

`104D6998 → DF60A950 → A450870F → 5E6A3B95 → E423CA14 → 939534BB / 88D12BAC`。

后两条从事务取出 `HappinessToken` 并写入住宅本地；其中一条还一起取回剩余 `MoneyToken`。所以最小住宅与商业配方都必须保持消费者的出发、实际购物、返家与结果接收，不能只保证店里有人和楼里人口非零。该规则链是源数据证据，不代表截图选中的伍德兰公园馆在当前存档已成功执行它。

# 手动设施与经营行为的边界

用户要求：商业使用巨塔商场配方；住宅允许居民不满、迁出，但经营状态不能导致手动设施废弃。住宅本身不被强制改成巨塔住宅楼层。

## 商业构建约束

新 Copan 基底路径将旧商业选择转成 EP1 巨塔商场选择，保留作者填写的客流、货物和岗位参数。W1/W3 转成对应收入档的商场入口，W2 使用 W2 商场入口。未知配方报错，不能回落到自长商业。

写盘回读必须确认商业使用巨塔收入契约、启用 DD6E83EC / F51AB185，且 6827D125 / 6827D126 / 6827D127 自长商业利润周期均不活跃。参考原版商场 61EFC000:8A807C96 及 `behavior_commercial_mall.rs`、`behavior_commercial_mixed.rs`。

## 住宅研究边界

原版住宅核心的 246F5982 → 96FAFAE6 → 38127842 → 74A1CA8E → 249E4DFC → 7362794B → 85BF39A2 链条包含空置和废弃状态。246F5982 的本地条件 mask=0000020000005000、value=0000000000004000，要求 Normal=1、Burning=0、IsToy=0。因此不能把自长住宅的生命周期直接视作 plop 生命周期。

采集到的原版巨塔住宅实例具有 IsToy=1，但仅据此阻断整条链不能证明不满意迁出仍能正常运行。不能用固定人口、强制幸福、伪造着火状态或忽略返回闭环来实现“不会废弃”。仍需核实私有住宅单元的原生身份、迁出、补入住与住户工作/消费/上学返回。

证据位于 `tmp/residence-minimal-loop-20261125/decoded-rules.json`、`runtime-reference-comparison.json` 和 `residence-loop-contract.json`。当前结论属于属性数据与离线规则分析；不代表新构建已经获得游戏运行验收。完整设施的水电、污水、垃圾、总开关、30645625 生命周期与渲染闸门继续适用。

## 基底已经落到构建器的边界

`behavior_copan_base.rs` 使用 SHA-256 固定为 `8a9f05319dc140dbbf4a2313ab638a5d3341c24b7cdb95940ee15da4364fc5b8` 的公共层原型。来源为科潘 `4DC31F9B` 继承链，剥离住宅叶和地标业务层，保留普通 plop 公共层 `2A25CF66 → F98BCB35 → 9EC474FF → 593B61D2`。35 个有效 bundle、105 列；提取审计在 `tmp/residence-minimal-loop-20261125/copan-basic-plop-audit.json`。

基底保留水电、垃圾、污水、整体开关和 `30645625` 生命周期。设施岗位直接在宿主上编译；业务岗位属于业务组件。新路径清除旧劳工编译器的学校父模板和学校类型覆盖，宿主与组件的 `0AFE27B1` 必须保留原型的普通 plop 类型。裸基底有单独的完整菜单验证入口，仍检查组件表、源内景、灯光控制和统计柱，不伪造子单元来满足旧容器验证器。

住宅组件另按科潘叶 `40E0C000:4DC31F9B` 原始排除表保留 `30645625` 排除，必须启用自己的 `933F0FBF/9DEF44FB` 住宅状态／入住资源支持。宿主继续保留 `30645625`。这是两个 Unit 的不同职责，不得为了修宿主夜灯而把设施生命周期重新带进住宅组件。写盘闸门同时检查宿主保留、住宅组件排除；回归测试重新启用组件上的设施生命周期必须失败。

## 原设计面板的实际单元查询

原设计的住宅反馈、地价住宅、幸福／悲伤原因和观光收入不能直接读取业务为空的宿主，也不能把多个 Unit 的控制位相加。新 `panel/component_queries.rs` 仅为恰有一个对应业务组件、且共用建筑位置的配置生成明确的 child entry ID 选择器。重复或无法确定的对应关系继续拒绝。

住宅组件 Lot 仅迁入原版 `0D5A1674` 文字表列 `TextFeedbackResidentialW1Rollover.json`，不迁入科潘完整图形模板。列的独立原始编码 SHA-256 为 `f82e5393c61ae98fac2da77eb36e5b22668e95d25839e9078f2db96eb5e68a50`；来源与三个 RCI 住宅供体交叉核对，记录在 `residential-panel-metadata.json`。缺失或更改该列会使写盘校验失败。

原生接口证据：`docs/source-code/SimCity-dev-ida.c:779121` 的 `units/match/all/unitID-…` 用 `StrtoU64` 解析 entry ID，`779219–779254` 明确通过 `SetArrayType/SetArrayValue` 返回数组。`769640–769676` 的 UnitRef 是 `{slot, stamp}` 对象。此前 v4 的适配错误地把 match 结果当成按引用索引的字典，已纠正；v4 面板运行包不可部署。修正后的实现分别查询相同过滤器的 UnitRef 数组和位置数组，唯一位置匹配后，下一次查询再验证 stamped ref 和真实位置。数组长度不一致、引用失效、位置歧义均不猜测。成功定位后缓存引用；丢失时退避，不每帧扫描全城。

## 服务状态边界与组装层修正

旧共享位置组件经过 `exclude_child_utility_connections`，排除了 `48939D96/825B4CA4`。原有闸门只验证连接没有重复，不能证明宿主的停水／停电会驱动子业务状态。普通 native `ConnectUnits` 维护连接表和 sink，不能仅凭连接表声称控制位会镜像。

对基础与 EP1 两份完整 UnitRule 库扫描共 33,926 条记录，发现 12 个本地 Power/Water 位写入规则；结果在 `all-native-utility-flag-writers.json`。执行器 `SimCity-dev-ida.c:697240–697268` 把局部掩码写回当前 Unit、全局掩码写回全局集合，未由这段代码证实宿主到子 Unit 的镜像。原版楼层自身包含真实水电消费路径。因此八组构建写盘通过不能证明此项运行闭环通过。

新 Copan v6 路由改为由组装层保留每个执行单元的真实 `48939D96/825B4CA4`。住宅、商业、观光、办公室叶子不新增供能参数；`behavior_copan_services.rs` 从宿主作者配置或已固定的原型默认值读取整栋预算，在宿主及组件之间作确定的整数商余分配。各单元 Amount 均为正整数，Capacity 与伴生 Capacity 各为其 Amount 的三倍，周期与作者配置相同；整栋用量和两份容量合计必须等于原配置。原版绑定表 `0A6FE749–0A6FE74E` 把这些 Float 属性送入 Power/Water 及 Needed 槽，因此初始库存也没有被复制增加。

例如完整四业务加宿主共 5 个执行单元，原型整栋电量 12、水量 10：电量分配 3/3/2/2/2，用水均为 2；电容量合计仍为 36，两份水容量合计各仍为 30；原生周期均为 72。没有写入 Power/Water 控制位，没有空需求观察器，没有增加整栋需求，没有替换本地失供／恢复规则。旧路由保持原行为；v6 写盘验证逐单元检查实际 provider、八项用量／容量／周期，并核对整栋合计，丢 provider、改量或改汇总都会失败。

这是新的组装预算契约，不冒称原版存在一个自动分摊函数。原生消费者使用整数 bin；用量不足以分给每个执行单元正整数份额、不能以 Float 精确表达、容量不符合原生绑定时明确拒绝。静态守恒与链条完整不替代游戏内道路供给、停水停电及恢复的验收。住宅 `IsToy` 对经济废弃链的阻断与不满意迁出也须分别说明，不能合并成一句“住宅正常”。

## v7 住宅空位、迁出和补入住分区

`behavior_copan_residence.rs` 在新 Copan 路由上接入原版三档 `78A730CD/CE/CF` 入住入口，并将 `EBFC1753/1750/1751` 中的住宅空位与迁出部分生成一个私有 bundle。原有地面住宅共同核心和作者人口、劳工、消费者、儿童、幸福容量参数继续保留。旧地面入住入口和整份 EBFC bundle 被排除，避免两个入口同时更改空位池。没有清除 IsToy 来强开自长住宅经济链，没有填充固定住户，也没有新增 AEB 规则。

三档空位/迁出根分别为 `387158A8 / 919D0D97 / 80710E4E`。依赖分析覆盖周期、事件、sink 和 `0C614160` 玩家开关入口，选中分支未发现写 Abandoned 的规则；这属于原版规则分析结论，不能代替游戏中迁出和重新入住的事实。`0E546792` 是密度升级参数，不作迁出成本解释。

明确剥离的根：W1 为 `1E2BCEE8, BA1547D0, 8E527F31, 737991EA, D500B08A, 4E197A34`；W2 为 `C1CF708D, BA1547D0, 8E527F31, 737991E9, FFFBDFE3, 92AE0775`；W3 为 `4319F62E, BA1547D0, 8E527F31, 737991E8, 650914DC, 9A4DFB96`。这些分别对应楼层租金、楼层费用发布、巨塔公园层加成、楼层注册及配对清理。同步移除各档楼层计数 bin `F42A61C8 / FA0AD4F5 / 1796D426` 和塔内公园加成累计 `F6FC5D0D`，保留其余九行原生 bin 容量、初始化和绑定。没有迁入楼层 Unit、塔身份或建造属性。

原生 `0C614160` 不是说明字段，而是整栋开关的玩家规则列；三条回调完整保留，不能只看周期根就裁掉。执行证据为反编译源 `PlayerRulesFromScripts`（654043）、`AddBundle`（699034）、`FillFromProps`（700035）和 `RunUnitAndAttachedPlayerRule`（1139967）。返家学生的原版双 handler 也保留；不能仅按 sink 名字重复就去重。清理输入 `0E816C38=100` 来自原版住宅，按原始单列编码校验。`0DB653A1=FAE85276` 由公共基底已有列提供，不另造默认值。

有作者车辆路径时，新绑定器在保留既有地面返家车流接线后，增加当前真实 `78A730C*` 入住 sink 到原生 `03106C2E` 的入口行，保留方向列长度和原有路径校验。没有作者车道时不虚构路径几何。写盘层检查原生入口唯一、竞争入口排除、私有 bundle 内容、九行 bin、完整玩家回调、清理参数以及宿主/住宅各自的生命周期；缺 bundle 或删回调的变异测试必须失败。

原始文件身份和裁剪依据在 `src-tauri/resources/sc5/residence-balance/README.md`；详细提取与依赖记录位于 `tmp/residence-minimal-loop-20261125/{balance-source-extraction,apartment-balance-boundary}.json`。旧路径不接入此适配。实际居民上班、消费、上学、返家、不满迁出、补入住，以及关闭重开、供能和灯光仍须在隔离城市逐项验收。

实际和平饭店生产构建曾拦截到分区后的 `0A0209A4` 空数组列。原版布局用缺省列表示空启用层，不能写 `count=0`；适配器据此省略该列，同时住宅写盘校验拒绝任何空数组，变异测试覆盖此项。没有绕开既有布局校验。

完整生产 API 还拦截到私有 bundle 引用缺类型/组的身份闭包缺陷：原生 stock 脚本可用零类型/组的 ID 引用，自有资源必须像既有收入适配器一样写完整 TGI。新住宅 bundle 据此使用 `00B1B104:40E0C700:<private>` 的完整引用。集成测试在实际 `retain_identity_closure` 后再次执行完整行为验证，防止资源在组装时存在却在输出闭包中被裁掉。

中国银行额外的四业务组合检查因保留场景缺完整通行路径表，被既有 `BEHAVIOR_UNIT_PATH` 拦截。其裸基底渲染验证与组合行为验证分开记录；没有虚构入口或把裸基底通过写成组合通过。
